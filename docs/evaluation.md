# 怎么评测这个插件

结论先写：**经济性可以自动量、可以对账；质量不能从账本里读出来，只能同任务开关对照。**
把这两件事混在一起看，就会得出「省了很多 token，所以很好」或者「召回了 11 次，所以退化」这类都站不住的结论。

---

## 一、经济性：只认 provider 回报

### 指标

| 指标 | 从哪来 | 说明 |
| --- | --- | --- |
| 每轮 prompt token | 会话日志 `assistant/message.data.usage` | 实测，不是估算；包含命中、未命中、写缓存三档 |
| 每轮金额 | 同上 × 三档单价（峰时乘峰值倍率） | 唯一能拿去和账单对账的数 |
| 命中率 | `cacheRead / (cacheRead + input + cacheWrite)` | 折叠是否把前缀缓存打坏了，看这个 |
| 上下文峰值 / 末次 | 每步 `input + cacheRead` 的最大值 | 折叠真正的作用：把峰值压在窗口以内 |
| 折叠固定开销 | 检查点字符 ÷ 4 | 每轮新增一条摘要，之后每个请求都要重发它 |
| 召回开销 | fold-store 的 `recall` 记录 | 模型回去翻原文的输入成本 |
| 重要消息开销 | fold-store 的 `pin` 记录 | 每次请求都重发，随轮次线性累积 |

### 必须先纠正的一个直觉

「折叠每轮都改写前缀，所以缓存全废、每轮要重发整个上下文」——**实测不成立**。

本会话 57 轮、2335 步：首步未命中合计只占全部未命中的 **14%**，单轮中位数约 **2.5K token**。
原因是替换点落在轮末：检查点插在上一轮内容的位置上，它前面的前缀一个字节没动，缓存继续命中；
变动的只有「检查点 + 新用户消息」这一小段。

这条决定了折叠的经济性：如果每次折叠都要重读 100K 上下文，它一定是负收益；实际不是。

### 不要用「不折叠会花多少」当账单

账本里的不折叠视角是**重放模型**（`lib/cost.js`），它回答「如果这些历史原样重发」，不是真实计费。
真实请求还会被请求期压缩器（billion-context）改写成它自己的摘要，所以反事实值会系统性偏高。
要拿这个数做决策，先看账本里的 `drift` 拆解，再决定信几分。

## 二、质量：只能对照，不能凭账本

### 为什么代理指标不够

从 fold-store 能读出来的行为指标只有三类：

- **召回/轮**：本会话 0.19（11 次 / 57 轮）。
- **重复召回**：同一段被召回两次以上，本会话 3 段。
- **跨轮重复调用**：同一「工具名 + 参数」在更早轮次出现过、之后又调一次，本会话 3 / 2113。

它们都只能当**线索**。低召回率既可能是「摘要够用」，也可能是「模型没意识到自己忘了」——
后者恰恰是最危险的退化，而它在日志里什么都不留。跨轮重复调用同理：正常任务也会重复跑同一条命令。

### 能下结论的做法：同任务开关对照

1. **任务集**覆盖五种形态，各 2~3 个：
   - 长调试（读日志、改代码、跑测试，轮次多、工具输出大）
   - 多文件改造（跨文件一致性，靠记住早先的改动）
   - 资料检索（大量读取、少量结论）
   - 单点问答（本来就该走短轮，用来看折叠会不会误伤）
   - 超长连续任务（20 轮以上，看上下文是否还稳）
2. **两个臂**：A 开折叠、B 关折叠（`fold_config({action:"set", patch:{enabled:false}})`）。
   配置是进程级全局的，所以只能**顺序跑**，不能并行。
3. **每臂新会话**，同一个模型、同一份任务、同一套工具。
4. 记录：任务是否完成、步数、token、金额、耗时，以及人工（或另起一个评审模型）按同一份标准判分。
5. **配对比较**：同一任务的 A/B 成对相减，再看分布；不要拿不同任务的总平均互相比。

### 判据

- 经济：每轮金额或每轮 prompt token **显著下降**（配对差值的中位数与区间，不只看总和）。
- 质量：成功率**不下降**（非劣效），重复劳动不显著上升。
- 只有经济降、质量也降，就要算「省下的钱值不值多花的返工」；两边都降就调参或关掉。

### 一个绕不开的混杂项

关掉折叠后，长任务会被 billion-context 压缩，于是 B 臂测到的是「折叠 vs 压缩代理」，不是「折叠 vs 什么都没有」。
- 想评「折叠本身」：把 bili 也关掉，但超过 1M 窗口的任务直接跑不完，只能选短任务。
- 想评「真实收益」：保持现状对比，这更接近你实际会遇到的组合。

本会话已经折掉 9.4M 字（约 2.35M token 的轮内产物），远超 1M 窗口——
**这类任务上「折不折」不是优化问题，是能不能跑完的问题**。所以质量对照要选能跑完的任务做。

## 三、稳定性

这些不需要跑任务，观察日志就够：

- `$DSH_HOME/dsh-fold-context.log` 里 `折叠失败` / `召回失败` 的条数；
- 重启后旧会话能否继续折叠与召回（fold-store 与会话日志都要在）；
- 折叠范围：主会话正常生成检查点；默认 `foldSubagents: false` 时子代理轮次保持原文、没有检查点，打开后子代理也折；普通子代理的工具清单里只有 `fold_pin`，fork 子会话多一个 `fold_recall`；
- 子代理里 `fold_pin` 可用，消息只出现在子会话日志里，父会话收不到；
- fork 出来的会话按父会话编号召回：父会话仍在进程里时应取回原文，父会话查不到时应返回「暂时读不到」而不是 not_found 或报错；
- 顶栏账本 / 模型视角 / 逐轮报告三个页面在会话不在进程里时是否返回明确原因而不是 500。

## 四、工具

### 离线评测器（本轮新增）

```
node tools/eval.mjs <会话 id> [--home <DSH_HOME>] [--json]
node tools/eval.mjs --ab <开了折叠的会话> <对照会话>
node tools/eval.mjs --list
```

只读两样东西：会话日志（provider 实测用量）和 `fold-store`（折叠/召回/固化记录）。
不读账本的反事实估算，所以结论能对账。

### 已有的页面

- 顶栏「折叠 · 账本」：实时 token 收支、构成占比、趋势、逐轮成本。
- 顶栏「折叠 · 模型视角」：模型实际看到的历史，检查点可展开对照原文。

## 五、判据之外的调参

两个旋钮决定「省多少 / 丢多少」：

| 旋钮 | 调大 | 调小 |
| --- | --- | --- |
| `minFoldRatio` | 折得更少，更安全也更贵 | 折得更多，省得多但更依赖摘要 |
| `maxNoteTokens` | 回复预览更完整，召回更少，但每轮都重发；markdown 回复超限时改列标题，不受此上限约束 | 回复预览更短，省得多，召回可能变多 |

调参也应该走同一套 A/B，不要凭单会话手感。

## 六、当前基线（本会话，2026-11-14）

```
轮 57 · 步 2335 · 折叠 56 段（原 9.4M 字 / 摘要 13.8K 字）
实测 prompt 201.4M（未命中 5.7M / 命中 195.8M） · 输出 1.9M · 命中率 97.2%
金额 ¥17.27（命中 ¥3.92 / 未命中 ¥5.68 / 输出 ¥7.68）
上下文峰值 204.2K · 末次 101.9K
召回 11 次 · 返回 10.8K token · 重复召回 3 段 · 重要消息 1 条
质量线索：召回/轮 0.19 · 跨轮重复调用 3 / 2113
```

读法：
- 输出占金额 44%——那是任务本身干的活，折叠管不到，别把它算进「折叠省了多少」。
- 未命中 ¥5.68 里，每轮首步只占 14%，其余是每一步新增的思考与工具结果。
- 上下文峰值 204K，说明折叠把 57 轮压在了 1M 窗口的 1/5 附近。

## 七、常见误判

1. 把账本「不折叠 = 1.2B token」当账单 → 那是重放估算，真实值会低很多，看 `drift`。
2. 只看总金额不看轮均 → 步数不同的两个会话没法比。
3. 用单会话、单任务外推 → 任务形态对成本的影响比折叠开关大。
4. 把「召回次数少」当成功 → 模型可能根本没意识到自己忘了，只有任务结果能证明。
5. 把输出 token 算进折叠收益 → 折叠只影响输入。
