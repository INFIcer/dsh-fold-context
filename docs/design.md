# 设计说明

## 为什么是「替换」而不是「改写请求」

DSH 的模型可见内容必须能从会话日志重建，所以插件不改模型请求，而是往 surface 上写一条真正的事件。
折叠 = `session.append('user/message', 检查点, { surfaceOp: { op: 'replace', startSeq, endSeq }, sourceEventSeqs })`。
这条事件遮蔽了本轮原有的节点，`deriveMessages()` 立刻反映新历史；重启后 seed 重放同一套校验，不需要任何迁移代码。

只写内置的 5 种 surface 类型之一，不自造事件类型，也不注册 message projection——插件卸载后旧会话仍然可读，只是检查点退化成普通的 user 消息。

## 切点为什么按「轮」而不是按 token

折叠的收益是前缀稳定：整轮替换后，下一次请求只在一个位置发生变化，前缀缓存最多失效一段，而不是被切碎成多处。
按 token 压缩需要预测哪些内容不再被用到，猜错的成本是模型失去依据；按轮折叠把预测推迟到召回时——召回是模型主动发起的，它比任何静态策略都清楚自己缺什么。

## 折叠粒度

片段从第一条非保留节点开始，包含它全部的 `tool/result`，遇到保留节点就断开。保留节点包括：用户原话、调度指令、重要消息、上一次的检查点、`system/message`，全部上下文注入（审批变化、子代理通知、工具变更、模型切换、运行时快照、时间上下文、技能目录……）与开发者消息。`system/message` 单独断开，是因为宿主常在两个被跟踪节点之间追加新的系统提示词，替换区间不能跨过它。
这样折叠区间总是落在整步上，不会把一次调用和它的结果切开，也不会让一个未完成的步骤消失；落单的 `tool/result` 直接跳过。
注入一概不能折，分两种：一次性注入（审批变化、子代理通知、工具变更、模型切换……）宿主不会补发，折掉就永久丢失；会重放的那三种——运行时快照（`runtime-context` + `snapshot`）、时间上下文（`time-context` + `snapshot`）、技能目录（`skill-catalog` + `catalog`）——宿主判断「发过没有」的依据是这条消息在 surface 上是否还看得见，折叠用 `replace` 把它移出 surface，宿主就当作没发过、下一步重新投影或重发一份。于是折掉省多少、重发补回多少，净收益为零，还多一条检查点；技能目录重发的是完整目录而不是增量，折它更是净亏。所以注入全部按 keeper 处理，真正值得折的是思考、工具输出与长回复。调度器投递的是用户指令（`source.kind === 'schedule'`），和用户原话一样是 keeper，折掉等于吞掉用户要求。
同一轮里如果用户插话或模型发了重要消息，片段会被切成多段，每段各自替换成一条检查点。

文件、记忆与技能的正文不该折成摘要：它们不是「这一轮做了什么」的经过，而是之后要照着执行或引用的依据，摘要会让模型拿着模糊印象做错事。早先试过按工具名、路径片段与代码里的文件 API 自动识别，结论是识别不准：本机几乎所有操作都经 `run_code`，扫代码里的 `readFileSync(` 会把绝大部分步骤都判成受保护，折叠等于关掉；反过来，模型换一种读法就漏掉。于是改成显式声明：需要长期保住的内容由模型用 `fold_pin` 固化，pin 是 user 消息，天然不进折叠片段。提示段给出触发条件（用户提到记忆、备忘、技能、长期约定，或模型自己读到、写下以后还要照着用的内容），并允许逐字抄原文——规则和事实压缩不得。插件不再自动判断哪一步该留，代价是漏固化时内容仍会被折掉，只能靠召回补回（技能加载是唯一没有用户提示兜底的场景，所以在提示段里单独点明）。

## 可调参数与运行时配置

折叠力度不该写死在代码里：同一套阈值在短会话里折得太碎，在长会话里又太粗。参数集中到 `lib/config.js` 的 `FIELDS`，字段白名单只有这一处，默认值、类型、范围、说明都从这里生成。

配置分三层：默认值 < profile 里的 `config` < `$DSH_HOME/fold-config.json`。文件放在最后，是为了让人手工改文件能压过 profile 里的旧值。

文件层只保存**显式改过的键**：`set` 一个键时只追加这个键，不会把 profile 里其它值一起冻结进文件（早先写的是合并后的整份快照，之后改 profile 永远不生效）。`reset` 则把全部字段显式写成默认值，因此会压过 profile；想回到 profile 的配置就删掉文件或写成 `{}`。这样「升级默认值」与「reset 真的 reset」两个要求都能满足。

数值型默认值在加载时本来就取代码里的当前值，文本型不行：文件里存的是整段文案，旧文案与升级后的默认值无从区分。所以写盘时把「值恰好等于默认值」的字符串键记进 `_fromCodeDefault`，加载时这些键改取当前默认值——只跟随代码、不覆盖用户自定义的文案。

两条校验路径刻意不同：

- 加载时钳制：`normalizeConfig` 把越界数字夹回区间、类型不对就保留基线值、未知键忽略并 `warn`。目标是「配置写坏也能起」。
- 运行时修改严格拒绝：`validateConfigPatch` 对 `fold_config` 的 patch 逐项检查，未知键、类型错、越界、字符串超长都返回原因，整批不生效。目标是「模型不会误以为改成功了」。

### 总开关：关掉的是「模型侧的一切」

`enabled` 不是「只停折叠」。关掉之后插件在模型面前完全消失：不折叠、不注入系统提示段、也不注册三个工具——只有这样才能让账本口径等于「没装这个插件」，和预测逐项对账。同理，关掉时不补发重要消息：补发也是一条消息，会把未压缩的基线搅浑。

代价是这些状态没法靠工具自己改回来（`fold_config` 也一起没了），所以开关的入口必须在宿主侧：顶栏折叠页与插件设置页直接读载荷文件与配置文件，不受开关影响；改完写进配置文件，下一轮 `reloadConfig` 发现翻转后把提示段与工具重新挂上，不用重启。摘工具要挪一跳（`setTimeout 0`）：关掉开关的那次调用往往就是 `fold_config` 自己，同步 dispose 会在它自己的执行途中把注册项摘掉。

### 折与不折：minFoldRatio 与 maxNoteTokens

折与不折按比例判断：摘要长度低于原文的 `minFoldRatio` 倍（默认 0.5，即至少省一半）才替换，否则保留原文。省不下多少的时候，替换的收益抵不过一次前缀变化与一条检查点的开销。这个比例是二选一的判据，不是压缩摘要长度的旋钮：检查点与目录整体两处拿它决定「折还是留原文」，摘要本身该多长由各自的设置决定（回复预览的 `maxNoteTokens`、目录预览的 `recallIndexPreviewTokens`）；目录每行则在预览与原文之间直接比长短，不用比例。

摘要长度由两部分相加：**元信息**（编号、思考段数、工具调用、文件行、工具输出段数）与回复预览。元信息的长度能从 stats 精确算出；回复预览的长度同样能当场算出：不超上限时原样保留，超过时 markdown 回复按标题摘要（标题清单当场列出来，比原文长就保留原文），其它回复取开头+结尾。因此折叠前估算与构建后复核用的是同一套精确长度，不需要任何「预留」；`maxNoteTokens` 只决定回复从哪一刻起改用节选或标题摘要，不参与长度预留。

元信息永不被截断——它们是模型判断「要不要重读、该召回哪一段」的依据，被回复挤掉就失去了检查点的意义。回复不超过上限时原样保留、只出现一次；超过才取开头（约 3/4）与结尾（约 1/4），两者合计不超过上限，并加省略号。

回复是 markdown（至少两个 ATX 标题）时，超过上限改为按标题摘要：每个标题都列出来，连成「# 结论 / ## 改动 / ## 验证」，不截断也不带正文。标题清单本身就是取回索引——模型看到「## 验证」就知道该去召回哪一节，开头和结尾反而可能都在同一节里。实际长度不受 `maxNoteTokens` 约束，也不按它预留：清单长度由原文结构决定、当场算出；只有标题连起来比原文还长时，才退回原文。只有一个标题不算目录（没有信息量），退回默认节选；围栏代码块里的 `#` 不算标题。

### 工具输出要不要折：foldToolOutputs

默认 `true`。设成 `false` 时工具输出不进摘要、不进召回载荷，也不计入 `minFoldRatio` 判断的原文长度——几处口径必须一致，否则会出现「摘要说折了、召回却拿不到」或「比例按含工具输出算、载荷里却没有」的错位。适合工具输出另有日志可查、只想折叠思考与回复的场景。

### 每轮折几段：maxFoldsPerTurn

同一轮里用户插话或模型发重要消息会把片段切成多段。每段都是一次 surface replace，都会让下一次请求的前缀变化一次；默认 8 段是上限，超出的片段保留原文，宁可少折也不让前缀抖成筛子。

### 载荷存储与容量

`fold-store` 的读路径只解析一次：每个会话的文件在第一次访问时进内存索引，之后 `findFold` / `recallCount` / `pins` 都走内存，append 追加一行并同步更新索引。早先每个操作都重读整个 JSONL，而且发生在 `turn-stopping` 的同步路径上，会话越长轮末阻塞越久。

容量由 `maxStoreTokens` 控制（默认 200 万 token 估算 / 会话，0 为不限）。超出时重写文件：保留全部 pin 与召回记录，fold 载荷从新到旧装，装不下的编号记进一条 `prune` 记录；最新的一条 fold 无条件保留（它最可能被召回）。被清理的编号在召回时明确回「已因存储上限被清理」，而不是含糊的「没有记录」。append 前若发现文件末尾是半行（上次进程被杀），先补一个换行，避免新记录接在半行后面一起丢。

### 文案与排序

`systemPromptText` 可整段替换提示词，支持 `{{recallTool}}`、`{{pinTool}}`、`{{configTool}}`；`recallReminderText` 控制召回超阈值时的提醒，支持 `{count}`、`{tool}`。占位符都是字面替换，不认识的占位原样保留，不会因为配置里多写了一个占位就整段消失。`promptOrder` 决定提示段插在哪，默认 300。

### fold_config：运行时读写

`fold_config` 有三个动作：`get` 返回当前生效配置、文件路径与每项范围；`set` 收一个白名单 patch；`reset` 把全部字段写成默认值。`set`/`reset` 走宿主注入的 `updateConfig(patch)`：只把 patch 合并进文件层，再重算生效配置并立即生效。写文件失败会抛错，工具明确返回「未生效」，不会出现「内存改了、磁盘没写」的假成功；宿主没接线 `updateConfig` 时退回只写文件层。

## 子代理与 fork：折叠按会话启用

折叠是优化，要不要折取决于会话的寿命与产物。子代理短命、派回父代理的只有最终回答，折它省不下多少，还多留一份 `fold-store`；所以默认只在主会话折叠（`foldSubagents: false`），要折再显式打开。

- 判定只看 `session.header.origin`：`subagent` 的会话不折，fork 出来的子会话同样如此。三个落点共用这一个判断——`foldTurn` 的两个调用处（`agent/turn-stopping` 与 `turn/end` 兜底）与工具/提示段的可见性。
- 提示段用函数形式按 assembly 的 `context.agent` 现算：主会话给完整说明；子代理给一段短提示——本会话不折叠、`fold_pin` 只对自己可见、要交出去的结论写进最终回答；`isSeeded` 的 fork 子会话再多一句「历史里的检查点来自父会话，仍可用 `fold_recall` 按编号取回」。`systemPromptText` 被显式配成空串时，任何会话都不注入。
- 工具跟着折叠范围走：普通子代理只剩 `fold_pin`；fork 子会话多一个 `fold_recall`（否则 seed 里的检查点没有出口）；`fold_config` 只在启用了折叠的会话里出现。判定用宿主注册项的 `when`（`ToolActivationContext.agent`），声明与派发一起生效，不是只藏 schema。
- 子代理里 `fold_pin` 照常可用：它只 `append` 到子会话自己的日志、写子会话自己的账本；父代理的收盘通知只取子代理最后的 assistant 文本，所以 pin 传不出去。这个边界写在提示段、工具描述与回执里，而不是替模型拒绝——「给自己留备忘」本身是有效用法，要交给父代理的结论必须写进最终回答。
- fork 子会话的 seed 带着父会话的检查点编号，载荷在父会话的文件里。`FoldStore.findFold` / `isPruned` 在本地未命中时沿 `header.parentSession` 只读回退到父 store，多级 fork 天然串起来；只有「父会话仍在会话表里」才回退，否则报「父会话不可达」。`readAll` / `folds` / `pins` 不跨父：账本按会话计价，跨父汇总会把父会话的折叠重复计一遍；写入也只写当前会话。不复制父记录，因为复制只解决历史、不解决父会话后续新增的折叠。
- `fold_config` 在子代理里只读：`get` 照常，`set`/`reset` 拒绝。配置是进程级的，子代理改一次会同时影响主会话与所有并行子代理（包括总开关）。

配套：折叠日志带 `session=<前 8 位>` 与 `parent=<前 8 位>`，并行的多个子代理才分得清是谁；启动日志写明折叠范围（「仅主会话 / 含子代理会话」）。

## 触发点

`agent/turn-stopping` 是轮即将关闭、`turn/end` 尚未落盘的串行钩子：此时不在任何 append 的发布临界区，可以同步写；`turn/end` 时本轮内容还没散，节点也齐全。
作为兜底，`session/event` 观察到 `turn/end` 时排一个 0ms 定时器再补一次（观察者内同步 append 会撞上重入禁令）；已经折过的轮子再折一次是空操作，因为检查点本身属于「不折」的那一类。

## 重要的信息为什么能不被折

折叠是机械规则，它不理解语义，所以判断「什么日后还会用到」交给模型，插件只提供落点与压力：

- 软性：系统提示词告诉模型，跨轮会复用的结论、约束、路径、接口与数字都应该及早用 `fold_pin` 固化，不必等被反复召回；正文允许逐字抄、允许冗余，优先保真。
- 客观指标：召回次数会累加，超过阈值时工具返回里直接要求「这条已被召回 N 次，把可复用的结论固化下来」。
- 用户可以直接说哪些内容要留，模型据此调用 `fold_pin`。

不追求一次判断准确：召回本身就是事后评估，判断错了下一轮还能补。

### 为什么重要消息不设硬配额

早些版本给 `fold_pin` 设了条数（12）与总预算的硬上限，超了直接拒绝发布。结果正好卡在它最该起作用的时候：模型被召回提醒后想固化，却因为「配额用完」收到一条错误，于是继续召回、继续丢上下文。

现在默认 `maxPins=0`、`pinBudgetTokens=0`、`maxPinTextTokens=0`，三者都表示不限制：条数与长度由模型自己判断。pin 的代价远小于反复召回的收益，所以提示词只给正向许可——正文可以逐字抄原文、允许冗余和重复背景，拿不准要不要写全时写全；判断交给模型，不靠硬闸门，也不靠「省上下文」的暗示。

软上限仍然保留给想设的人：把字段改成正数后，超限只在工具返回里追加一行提示，发布照常成功。硬拒绝换来的「确定性」不值得让模型在该记的时候不敢记。

### 重要消息分级：permanent 与 recent

`fold_pin` 有两种 `level`：

- `permanent`（省略时的默认）：头是 `【重要·永不折叠】 标题`，用于长期有效的结论、约束、规则与事实。
- `recent`：头是 `【近期重要·第N轮·可能过时】 标题`，用于临时但可能跨几轮用的信息。N 是发布时的会话轮次，与检查点的「第 N 轮已折叠」同一个计数口径，模型据此跟当前轮次比较。

级别只写在消息头与账本记录里（`level` 字段，只有 recent 才写），账本与页面都不加徽标。**不做自动过期、也不每轮改写消息**，理由有两条：

1. pin 是一条已经注入历史的 `user/message`，它此刻的文字就是模型看到的字。要在它「过时」时改写或删除，只能再追加一条新消息或替换 surface 节点，两种做法都在悄悄改写历史，模型会以为这条结论刚刚更新过。
2. 静默丢弃比留一条带过期标记的更危险：pin 里往往是路径、接口约定、规则原文，模型丢了它不会知道自己丢了，只会凭印象重做。头里写着发布轮次和「可能过时」，模型可以在使用前核实；把判断权留在模型手里，插件不替它认定哪条已经失效。

旧记录没有 `level` 字段，一律按 `permanent`；旧 pin 消息的永久头仍然能解析，升级不需要迁移。

## 与压缩引擎的关系

插件不碰 `compaction/*` 事件，也不参与摘要生成，只在原来的压缩引擎之外做「低增速」这一层。
两者可以并存：折叠管日常增速，compaction 管真正的超限清理。

不过官方压缩的检查点（`source.kind === 'compact-checkpoint'`）必须当 keeper：它本身就是一次摘要，再折一次模型视角里连「哪一段被压过」都看不见。它替换掉的区间还会把 `fold_pin` 一起卷进摘要——插件不补发：pin 是「这一轮觉得值得常驻」的判断，不是永久存储，长会话里重要性本来会随时间淡化，淡化交给压缩层做。账本会核对活会话里模型此刻可见的 pin，把被卷走的条目标成「已压缩」并从「当前常驻」里扣掉；会话不在进程里时拿不到这份信息，仍按旧口径估算。

### token 口径

账本与模型视角现在用同一把尺：每个内容块 `ceil(字符数 / 4) + 4`，工具调用的名字与参数各算一块，每条消息再加 4。这是宿主 token-meter 与侧栏「上下文」页（dsh-context）共用的经验公式，不是分词器。

早先的静态报告曾给两档（3.2 与 1.6 字符/token），本意是「中英之间给个区间」，结果是同一条历史在账本与报告里出现三个不同的数，用户第一反应是算错了。区间看似诚实，实际只是把不确定性摊在界面上；既然宿主已有唯一口径，就该跟它对齐。

我们的数字只覆盖折叠产物，不含系统提示词与工具定义，所以和「上下文」页的总占用不可直接比；对照时要么补上那两项，要么只看同一批消息的增量。

### 外部压缩代理

billion-context 在请求侧重写历史，不写 DSH 会话日志，也不读 `surfaceOp`；本插件在日志侧做替换。两者互不破坏，但代理会把压缩块范围内的检查点与 `fold_pin` 一起摘要掉——「永不折叠」只在本插件的表层成立。

因此检查点正文必须带 fold 编号：编号落在代理摘要里也还能用 `fold_recall` 从本地 `fold-store` 取回原文。pin 则不做常驻化：它只是历史里的一条消息，被代理或官方压缩卷走后不会补发，也不注入系统提示词去对抗前缀缓存。
## 顶栏账本：折叠是收益，召回与固化是成本

折叠本身有代价（下次请求前缀变化、摘要占位），只喊「省了」没有意义，所以顶栏那页把两边都摆出来：绿条是折叠省下的 token，红条是这一轮召回和重要消息的开销。

### 为什么数据不从 deriveMessages 来

模型视角（`GET /fold-view`）能拿到 `session.deriveMessages()`，所以它按模型真实视角逐条重建。账本路由不一样：它是无状态的 HTTP 请求，手里只有会话 id，而且每 5 秒被调一次——把会话拉起来、重建派生消息、再算 token，成本远高于它展示的数字本身。

因此 `lib/stats.js` 只吃 `fold-store` 的记录：折叠记录里已经写了原文总字符、摘要和逐条载荷，召回记录写了返回大小，重要消息记录写了正文。这些都是写入时的事实，不需要重新读会话。

代价是「折叠后真实占用」只能近似：页面显示的是折叠摘要与重要消息的 token 之和，不含其它历史。够用，因为这一页回答的是「这套机制到底赚不赚」，不是「当前上下文精确有多少」。

### 口径与宿主一致

`lib/tokens.js` 复刻 `dsh-token-meter` 的估算：每 4 字符 1 token，每个文本块再加 4 token（`BLOCK_OVERHEAD`）。折叠收益 = 载荷逐块的 token 和 − 摘要那一块的 token；召回成本 = 当时返回正文的 token；重要消息成本 = 它作为一条消息的 token。同一段文本在两处计算会得到同一个数，页脚也写明这一点，避免和宿主自己的用量对不上时怀疑数据错。

### 轮次归属与旧记录

新写的召回记录带 `turn`、正文字数与 token；重要消息记录带 `turn`。老记录没有这些字段，统计时退回到「按被召回折叠所在的轮」估算，并在界面上标 `estimated`。这样升级插件不会让历史数据消失，也不会假装精确。

### 为什么是轮询而不是 SSE

数据是几十条记录聚合出来的小 JSON，5 秒一拉足够。SSE 要维护连接、处理重连、在宿主侧保存订阅者，收益只是更实时——而折叠发生在轮末，本来就是分钟级的节奏。将来若要更实时，可以在 `foldTurn` 成功后向订阅者推一条事件，接口形状不用变。

### 请求开销：为什么按轮重放

账本原来的「收益」只比了末态大小，这解释不了「折叠到底省了多少次重复发送」。真实开销发生在每一次请求上：同一个前缀被重发 k 次，命中缓存的部分和未命中的部分价格不同。

因此 `lib/cost.js` 把两种历史各重放一遍。折叠后的视角用「累计历史（系统提示 + 各轮摘要）+ 上一轮检查点」当本轮请求内容，不折叠的视角用「累计原文」；重放量按 `k × 前缀 + 轮内原文 × (k−1)/2 + 轮内原文` 算，再按命中率拆成命中与未命中两档计价。关键点：

- **折叠发生在轮末**：本轮 `chars` 只剩用户原话 + 摘要，轮内真正在上下文里的是被折掉的原文（`unfoldedChars`）。按 `chars − checkpointChars` 算会让重放量只有实测账单的 1/120（本会话 668.7k vs 40.6M token），校准系数被顶到上限，估算与实测就永远对不上。
- 检查点只在下一轮开始出现，本轮自己的检查点不计入本轮请求（它写在轮末）。
- 折叠改写了前缀，上一轮检查点在本轮首请求是未命中的；但它在**本轮其余每一步**都在，所以按命中价重发 `steps-1` 次——早先只把它算了一次未命中，漏掉了后面的重发。
- 轮内原文首次上行按未命中付一次，其余按平均半步进拆档；不能再给它多算一次 `(1−命中率)`（那是同一批 token 的第二次未命中）。
- 系统提示按**当前版本**从第一个请求起计入：派生消息里它按版本更新的位置出现，但那个位置只是它被改写的时间，不是它开始被发送的时间。
- 没折叠的短回合整段仍是新内容，不会虚增节省。

命中率有两个：`cacheHitRate`（以及用实测总量反推的 `hitRate`）是「前缀里有多少真的命中了缓存」，默认 1（即按满命中估算；DeepSeek 实测约 97%），而不是「缓存价是输入价的几分之一」；`resendHitRate` 再扣掉每步新写进历史的内容，因为那部分按定义必定未命中，留在分母里会把纯重发的命中率系统性压低（实测 98.3% 的一轮，扣掉后接近 100%）。这个区分是踩过坑的：早先把 0.25 当成命中比例，看上去保守，实际却把 98% 本该计费的前缀压到 2% 按命中价、其余按 0 元——账单只有真账的三分之一。

### 未命中为什么不按体积放大

第一版把同一个命中率套在两种视角上：折叠视角重发 2 亿 token 算出 680 万未命中，不折叠视角重发 12 亿 token 就算出 4000 万未命中。数字自洽，物理不通——它等于假定「未命中与上下文体积成正比」。

会话日志里逐请求能看出不对：55 轮 2298 步的未命中只占 prompt 的 2.75%，每步未命中约 2.4 千 token，而当时的 prompt 从 4 万涨到 30 万 token，每步的比值反而在跌。原因很简单：一次请求里真正没命中的，是「上一次请求之后才写进历史的那点内容」——本步的思考、回复、工具结果。这部分折叠与不折叠完全相同，因为被折叠的是更早的历史。

那么体积差去哪了？全在命中的前缀里：不折叠时每一步要重发 6 倍的历史，但那 6 倍都是缓存命中的旧内容，只按命中价计。

所以模型改成：折叠视角的未命中按「重发量 × (1 − 命中率) + 新增」算；不折叠视角再减掉插件额外引入的首次上行内容——上一轮的检查点摘要、固化消息、召回返回的正文（本会话三样合计约 1.5 万 token）。原文两种视角都要付一次，所以不折叠的未命中只会更小；折叠省的本质在命中档（前缀小 5 倍），而不是在未命中档。把 6 倍体积算成 6 倍未命中是上一版的核心错误（3340 万 token）。

这笔「额外首次上行」按来源拆成四档报（`pluginOverhead`：检查点 / 召回原文 / 分段目录与检索 / 重要消息），因为混成一个数时，读者分不出「只给目录」那次调用到底花没花钱。分段目录与关键词检索也是 `fold_recall` 的工具结果，也是新写进上下文的一段正文，同样按未命中计价，只是不带原文：把它们并进「召回原文」会掩盖一份大折叠先给了多大的目录，算成 0 又会凭空少一笔开销。四档相加等于 `pluginOverheadTokens`，与不折叠基线的差额逐份对上。

`tokenOf` 只接受「字符数」。它曾经被传进固化消息的正文，`estimateChars` 对非数字静默返回 0，于是重要消息那一档长期算作 0：数字自洽、对账也看不出来，只是少了一笔。现在类型不对直接抛错。

缓存失效事件（系统提示改写等）也不按体积放大：本会话有 22 轮的首请求吃了 2.3–5.2 万未命中，而当时的 prompt 是 7.4–30 万 token，说明这家 provider 的缓存不是单条前缀链，改一块只赔那一块。把这类事件按体积外推会把差额放得更大。

光有重放还不够。请求期压缩器（如 billion-context）会在发出前再收缩一次上下文，每步的 token 密度（中文思考、工具 JSON、代码）也和「4 字符 1 token」的估算不同，所以按 surface 重放出来的 token 与 provider 计费量仍不相等（本会话反推系数约 1.4）。因此模型里留了一个反推步骤：拿到过 usage 就用实测总量反推 `promptScale`、`outputScale` 与实测命中率，再把系数套回全部轮次。估算是被实测钉住的，不是靠人调一个「看起来差不多」的折扣；系数被夹断时 `calibration` 会同时给出未夹断的 `rawPromptScale`，页面也写出夹断前倍数——夹断值不能拿来解释账单。

### 收益为什么用 token 计，金额只作折算

折叠的收益是「这些 token 没有被重发」，它不该折成人民币当收益：同一批 token 换成高峰价就翻倍，真实请求还会被缓存命中率、请求期压缩器和工具定义改写，最后算出来的钱既无法验证、也无法跨会话比较。所以账本顶部的收益与成本一律报 token，读数能直接对到上下文本身。

金额只回答另一个问题：「这些 token 按当前单价折算是多少」。它出现在成本参考的表格与「实测账单」里，用来和 provider 的计费对账。为了让对账成立，折算要分三档，因为三档 token 的价格差上百倍（空闲时段命中 0.02、未命中 1、输出 4，元 / 百万 token）。`lib/cost.js` 每轮同时给出 `foldedHitTokens` 与 `foldedInputTokens`（不折叠视角同理），`lib/pricing.js` 再把它们各乘自己那档单价。

命中与未命中的分档还要再对一次账：折叠视角就是实测的那一次运行，所以它的未命中总量应该等于 provider 回报的未命中总量。模型里「本轮新内容 + 上一轮检查点」是未命中的来源，工具定义、请求期注入和 token 密度没进模型，`calibration.missScale` 用实测未命中总量把它收口——只调整命中/未命中的分配，不改重放总量。

顶栏账本（`lib/stats.js`）只有 store 记录、没有重放，但金额用的是同一套分档：折叠省下的是之后每次重发的旧历史，`savedTokens × 之后步数 × 命中价`；摘要自己第一次上行按未命中价；召回按返回正文的 token 折一次未命中（它通常在轮末被再次折掉）；重要消息首次未命中、之后每步按命中价常驻。早期版本在这里用 `0.02×0.97+1×0.03=0.0494` 的「命中率加权输入均价」同时给折叠收益和召回定价，还漏乘重发步数——一个均价不可能同时给方向相反的两件事定价，这是这一页最需要记住的一条。

### 重要消息算哪几条

`fold_pin` 写进历史的是真实消息（`session.append`），载荷里的 `pin` 记录只是同一件事的副本。两者会漂移：载荷被整理、pin 在官方压缩里被卷走、补投成功但记录没落盘。账本一度只认载荷记录，于是既会给模型看不到的内容收钱（`pinsLost` 只标出来、成本照收），也会漏掉还在上下文里的那批——实测本会话账本 389 token、模型视角 3.8k token，差了一个数量级。

`lib/pins.js` 的 `resolvePins` 把两边合成一份清单：surface（派生消息里 `source.kind = pin` 的那些，连正文）是准的——它就是上下文里那些字；记录只补轮次与发布时间；记录里有、上下文里没了的标 `present: false`，只报体积（`pinLostTokens`）不进成本；上下文里有、记录里没有的标 `recorded: false`，照样按字数计价。拿不到活会话时 surface 为 `null`，退回旧口径（按记录算、`present` 未知），不把「读不到」当成「不存在」。

配对是一对一用掉的，而且**先认正文、再退到标题**：同一标题可能发布过多次（订正后重发），上下文里留的是新版那条消息。只按标题取「第一条没用掉的」记录，会把旧记录配给新消息，于是新记录被判成被卷走——而那正是模型看得见的正文。本会话就踩过：上下文里是订正版，账本却报「1 条已被压缩卷走」，其实被取代的是旧版本。

配对用尽后剩下的记录分三种，账本分开讲，因为「少了一条」「这条记重了」「被新版取代了」给人的判断完全不同：

- `duplicate`：正文与某条还在上下文里的记录完全一致，同一条消息被记了两遍（重发时旧的没清掉），报体积、不算少一条；
- `superseded`：标题与某条还在上下文里的消息相同、正文不同，是被重发的新版本取代的旧记录，不是被压缩卷走；
- 其余才是真被压缩卷走（`pinsLost`），只报体积（`pinLostTokens`），不进成本。

两种「不是真丢」的体积各自单列（`pinDuplicateChars`、`pinSupersededChars`），页面上的说明与卡片提示也逐项写出，数字之间能对上：上下文条数 + 三种缺席 = 载荷记录总数。

输出单独记是因为它不该参与「折叠省了多少」的比较——同一句回复折与不折都要生成一遍，做差必然为零。把它列进参考，是为了让参考值和 provider 回报的三档数字能逐项对上；如果只算输入，参考值会永远比实测小一截，看起来像估算失败。

单价是可配的，因为官方价会变、用户也可能用别的模型跑同一个会话（缓存命中价与输出价的倍率各家不同）。默认值取 DeepSeek 2026-11 的官方价目表（空闲时段；高峰是这套的两倍）；改单价只影响结算，不影响 token 估算本身，也不触发任何历史重算——账本每次请求都按当前单价现算。

### 实际请求为什么单独显示

估算量的是会话历史，provider 回报的是真正上行的 token。billion-context 这类代理在请求期又压缩了一次，两边的差可能很大（本会话实测过估算 37 万、provider 回报 8 万）。差不是估算算错了，是两句话口径不同，所以 `cost.drift` 把它拆成三段：

- `governedTokens`：归折叠管的部分，即插件生效后的历史加当前系统提示。这一段能和实测并排比。
- `legacyTokens`：插件生效前的那一轮，插件永远折不动它，实测里它已被请求期压缩器改写。把它单列，估算就不会看起来系统性偏高。
- `externalTokens`：实测减去 governed 的余量，来自历史之外——工具定义、请求期压缩器注入的摘要。

比调低估算系数诚实：估算不参与反事实推算，只当 ground truth；拆口径只改解释，不改账。

一开始这个差还有一半是我们的错：surface 里留着 6 份历史版本的系统提示词，统计时全算了进去，光这一项就多出十几万 token。宿主只把最后一条 `system` 当生效提示，于是 `excludeStaleSystem`（`lib/inspect.js`）把更早的版本从「模型视角」总量里扣掉，`lib/composition.js` 把它们标成 `reference` 只展示不计入，`lib/cost.js` 也只累加当前那条。另一半差额来自请求期压缩器，这部分不在本插件能看到的数据里。

### 客户端为什么手写

DSH 的客户端插件产物就是 `window.__ModuleLoader__.load({ id, factory })` 包住的 CJS，`require("react")` 由宿主给。这个页面只有一个 Tab、一张图表和两张表，引入 tsdown/vite 构建链只会让「改一行要重新打包」成为障碍；手写 `client/client.js` 后，改完刷新页面就生效。

## 逐轮视图：为什么这样分组

报告的主视图是「一轮一个 `<details>`，收起时只露用户原话与回复」。分组规则不是随手定的：

- **按用户消息切轮**：用户消息是人与模型共同的锚点，也是折叠规则里唯一「永不折叠」的类别，用它开一轮，报告的边界和折叠的边界就是同一个。
- **系统提示词就地成块**：`system/message` 会出现在历史中间（宿主换提示词或插件重建提示段时追加），它属于「那个时刻」，不属于某一轮。所以它就地开一个 system 组、同时切断当前轮：出现在轮与轮之间就夹在两轮之间，出现在轮中就把那一轮切成前后两半。代价比「整体抽到最前」小：抽到最前会让时间顺序失真，也没法表达「第 2 版提示词之后模型看到的历史变了」。
- **`schedule` 投递的消息算用户消息**：调度器发来的是用户指令，折掉等于吞掉用户要求，所以它和 `user` 走同一条「不折」分支。
- **检查点归上一轮**：一条检查点表达的就是「这一轮被折成了这样」，它是轮的结尾而不是下一轮的开头。
- **轮次号按顺序数，不用记录里的 `turn`**：记录里的 `turn` 是宿主进程内的计数器，重启后从 1 重来，拿它当全局轮号会串号。现在按用户消息出现的位置编号 1..N；第一次出现折叠记录之前、又没有折叠的轮标「插件生效前·未折叠」，没折叠且内容很少的标「内容较少·未折叠」。

## 为什么正文不截断

旧版为了控制报告体积，把每条消息压成 200 字预览加省略号。结果系统提示词（八万字）、用户原话、插件装上之前的那一轮，看上去都像被折叠或截断了——报告的显示方式被误读成了折叠的实际行为，而折叠本身没有任何问题。

现在所有正文完整渲染，长文本只加 `max-height` 滚动框，工具栏的「展开长文本」可以去掉高度限制。宁可文件大一点，也不让「没折叠」在视觉上像「折叠了」。

## 底色而不是字色

只改文字颜色，在几万字的报告里几乎看不出差别；折叠摘要与原文还都是灰底正文，更容易混。现在按消息类型给整块背景色：用户原话蓝、注入灰、检查点蓝灰、思考琥珀、调用靛、结果橙、回复绿、重要消息紫。摘要块带一条「以下是折叠掉的原文，报告替你摊开，模型看不到」的分隔线——颜色告诉眼睛这是什么，分隔线告诉它模型看不看得到。

## 页头为什么粘在视口上（以及为什么没有「刷新」按钮）

折叠页最上面是四张卡与两张图，往下几屏是明细表。翻到第三屏时，页头（标题、两个标签页、「更新于」）早就滚没了，想换到模型视角得先滚回顶部。

所以页头用 `position: sticky; top: 0`：宿主把对话内容放在 `overflow: auto` 的滚动容器里，粘住只影响本页内部，不改宿主布局。两个配套细节少一个就穿帮——底色必须不透明（否则正文从页头底下透出来），横向负边距吃掉面板留白（否则左右各留一条 22px 的缝，滚动时内容从缝里钻上去）。

「刷新」按钮删掉了。账本本来就每 5 秒自己拉一次，按钮唯一的用处是「立刻」，而它抢的是同一份数据；删掉之后页头右侧只剩一行「更新于 HH:MM:SS · 每 5 秒自动刷新」，读账的人一眼知道这份数字有多旧。那一行由当前标签页回填（账本给「更新于」，模型视角给「读取于」），换标签就清空——两页读取节奏不同，混在一行会让人以为刚刷新过。

模型视角不自动刷新：一次 `/fold-view` 就是一整份投影，反复拉会让每一张轮卡片整棵重渲染，正是先前卡顿的成因。所以那一页保留一个「重新读取」，文案写清楚这是手动动作。

## 在线入口

五个 `/fold-*` 路由只接受本机同源请求：`Host` 必须是回环地址（防 DNS rebinding），`Origin` 存在时必须与 `Host` 一致，`POST /fold-config` 必须是 `application/json`（跨站简单请求带不了 JSON，挡掉 CSRF）。宿主自己的 `/api` 有 token 校验，插件路由绕过了那一层，所以这层校验必须自己补。

可视化只有顶栏「折叠」页一个入口：账本读 `/fold-stats` 与 `/fold-composition`，模型视角读 `/fold-view` 与 `/fold-turn`。中间曾经有过一份服务端现算的单文件 HTML「逐轮报告」（`GET /fold-report`）和一个离线脚本 `tools/render-report.mjs`，两者都已删除：报告是静态快照，同一份 `buildReportModel` 的产物在模型视角里已经能按轮展开、按段对照、按引用跳转；多一份 HTML 渲染器，就多一份会与账本口径分叉的代码，也多吃一份维护。

插件不向模型暴露报告工具：报告是给人看的，放进工具表只会多占一份 schema。

## 分级召回：为什么先给目录

一段折叠原文可能是几十万字：思考、工具调用参数、工具输出全在里面。整段塞回上下文，既贵又淹没有用信息——模型真正需要的往往只是其中一两段。

所以 `fold_recall` 先算一份分段目录，再按可算的长度决定返回哪种形态：

- 目录整体省不到原文的 `minFoldRatio` 倍时，直接返回全文——「目录 + 二次召回」的往返比原文本身还贵，分级反而成了额外税。
- 否则返回分段目录——每段一行「#3 [工具结果] 1,234 字：开头预览」，外加类型统计与合计。每行在预览与原文之间只比长短：预览比原文短才用预览，否则整行给原文（短段截成预览不省字，还丢正文）；预览长度由 `recallIndexPreviewTokens` 决定，不按原文比例缩。模型看完目录，再用 `parts` 选段：`["1", "4-6"]` 选段号与区间，`["think"]` / `["tools"]` / `["reply"]` 选类型，`["all"]` 全要。一次可以多选，选中的段按段号升序拼回去。

分段单位不是「一条节点」而是「一个内容块」：同一条 assistant 消息里的思考、回复、工具调用各自成段，工具结果单独成段。这样模型能只要思考、不要工具输出。段号在一次折叠内连续，跨节点不重来，模型只需要记 `#3` 这种短编号。

回复块还有第二级切法：正文超过一次召回额度（`maxRecallTokens` 的 4 倍估算）且是 markdown 时，按标题切成独立段，标题前的导语单独成段；本来就短、能整段返回的回复不切。阈值取召回额度而不是摘要上限，是为了对齐「短内容保持原文召回」这条规则：能一次拿全的就不该让模型再拼一次。目录、`parts` 选择与关键词检索必须共用同一套切段选项，否则检索给出的段号与召回时的段号会错位。

目录本身也受 `maxRecallTokens` 约束：超了就按行截断，并明确说还有多少段、建议用哪个区间选。只查目录不增加「内容召回」计数——否则模型每看一眼目录就被提醒去固化，压力会失真。

目录/整段二选一的判断在服务端与客户端各实现一次（后者只用于折叠原文面板的「整段/目录」标注），阈值与行内取舍规则两端保持一致。

### 载荷必须完整：预算不能按摘要体量给

折叠载荷（`foldRecord.items`）是召回的唯一样本，所以它必须覆盖整段，包括最终回复。旧实现按 `totalChars`（思考 + 回复 + 工具输出）给载荷预算，但载荷里还有不进 `totalChars` 的文本：工具调用的参数（早先段内的注入消息也在其列，现在注入一律不折、不再进片段）。预算提前花完时就地截断，被丢掉的正好是段尾——最终回复与最后几步工具结果。

本会话 43 条折叠里有 37 条因此取不到自己的回复：模型召回长轮次时只看到过程，看不到结论，于是更倾向于重新读文件、重新推导。修复后写入时不再按 `totalChars` 估预算（`recallItems` 收到无上限预算），一次塞回多少仍由 `maxRecallTokens` 在召回时控制。旧记录可以按 `startSeq..endSeq` 从会话日志重建 `items` 来修，`note` 不用动。

补历史用 `node tools/repair-payloads.mjs <sessionId> [--home <DSH_HOME>] [--dry-run]`：它把多帧 zstd 会话日志逐帧解开、按 `surfaceOp` 重放 surface，只重写「区间里有节点、载荷里没有」的记录，写前备份 `.bak-<时间戳>`，pin / recall 与解析不了的行原样保留。判据在 `planRepair`，由 `tests/repair.test.js` 用假日志覆盖。

段的身份由段首前缀决定：只有助手生成的段（`[思考]` / `[回复]` / `[调用`）才可能在一段里同时含思考、回复与调用，才继续按行首前缀拆；工具结果、注入消息、开发者消息整段就是一个块。它们的正文经常引用本插件自己的标记——源码、报告、日志里都有 `[回复] ` 这种字样——再拆就会切出假回复段，把目录与分段召回一起带偏。助手段内部也只按生成顺序（思考 → 回复 → 调用）认标记：已经进入回复阶段后又出现 `[思考] ` 行，那是正文在引用，不是新块。


## 减少重复读取：文件清单与关键词检索

折叠的代价之一是「模型记得自己读过，但不记得读到了什么」。实测本会话 52 次 read 里有 7 次是「文件没改过却重读了一遍」——不是折叠造成的必然损失，而是两条线索同时缺失：摘要只写「run_code 7 次」，不写读过哪些文件；召回又必须知道折叠编号，模型手里只有路径。

### 摘要里的文件行

检查点摘要加一行 `· 文件：改过 lib/web.js；读过 lib/turns.js`，从本轮的工具调用参数里提取：

- **改过**来自写类工具（write / edit / apply_patch 等）的路径参数。语义很硬：文件内容变了，要用的就是新版本，重读是对的。
- **读过**来自其余工具的参数路径；`run_code` 与 `pwsh` 的参数里没有 `file_path`，所以再扫一遍代码字符串里的盘符绝对路径。它们也可能在写，但插件不知道写没写——摘要不替模型下结论，宁可让它误以为「读过」也不要误以为「没改过」。
- 同一文件既读又写时只出现在「改过」里；路径只留尾部两段（`E:/a/b/lib/tools.js` → `lib/tools.js`），省字且够认。
- 这一行放在「工具调用 N 次」之后、回复预览之前：预算不够时先砍回复预览，因为「该不该重读」比「回复原话怎么开头」更影响下一步动作。

### 关键词检索

`fold_recall({query: "lib/web.js"})` 扫全部折叠的原文，只回「折叠编号 + 段号 + 命中位置附近的一小段」，不回原文：

- 多个词是 AND：同时出现才算命中，避免「随便哪个词沾边」的噪声。
- 片段从最早命中位置往前一点开始截，而不是取段首——段首常常是 `[工具结果]` 之类的标签，说明不了这一段是什么。
- 结果的排序是最近的折叠在前：同一个文件往往在最后一轮被读过，要取就该取那一版。
- 检索**不增加召回次数**。召回计数是「这段内容被反复取回来用」的客观信号，检索只是目录查询；把它算进去，固化提醒会在模型还没读原文时就开始催，压力失真。代价是检索本身也花 token，账本照记它的字符数。
- 编号 + 关键词同时给，就只在那条折叠里筛段，等价于「带条件的二级召回」。

### 这两条不解决什么

检索只能定位，不能判断内容是否还对：文件被改过之后，旧原文依然会被搜到，模型必须看摘要里的「改过」再决定重读。这仍是一条软性规则，靠提示词要求「只读过的先检索、改过的重读」；插件不做内容哈希，也不跟踪文件版本——那需要文件系统监听，超出「不碰外部状态」的边界。

## 模型视角：为什么这样排

模型视角页回答的是「模型此刻到底看到了什么」，所以它的顺序必须等于派生消息的顺序，不能为了好看重排：

- **重要消息按时间顺序贴在轮次之后**：这一页的职责是复现模型看到的历史顺序。抽到页顶就成了一份摘要，读者会以为约束是后加的；贴在出现位置之后，才看得出「这条约束是在第几轮、看到什么之后立下的」。轮卡片头部的紫色 chip 负责扫读。
- **系统提示词按出现时间成块**：提示词换版是历史事件，第 2 版之后模型看到的世界变了；把它抽到最前，就等于假装整个会话都在用最后一版。
- **第 2 版起默认只看差异**：两版提示词动辄七八万字，逐版全文铺开既占体积也看不出改了什么。`lib/diff.js` 剥掉公共前后缀再做 LCS，只给改动区间加两行上下文；`maxCells` 与 `maxDiffLines` 兜住极端输入，超预算就退化成「整段删除 + 新增」或直接标 `truncated`。
- **第 1 版必须给全文**：没有前一版就没有差异可看，而第 1 版恰恰是模型自我认识的全部依据。

## UI 折叠：为什么不是渲染完再隐藏

一份长会话的模型视角有一百多万字。`<details>` 收起时内容仍在 DOM 里，浏览器照样要解析、排版、占内存，用户看到的就是点开这页先卡两秒。

所以卡片收起时根本不挂正文：`useLazyOpen()` 用 `onToggle` 读 `event.currentTarget.open`，关着就返回空 body。折叠掉的原文同理，每段一个独立的 `<details>`，展开一段才渲染一段——二百多段的旧轮次也不会一次摊开。

不挂 DOM 只是省掉渲染；首包仍会把整份历史逐条带过来，长会话十几 MB，浏览器先卡在 `JSON.parse` 与常驻内存上。所以首包只留分组头（轮号、步数、字数、用户与回复的预览文本）与必须常显的重要消息；轮内条目与折叠原文由一个按需接口给，展开哪一轮就取哪一轮。

召回结果（`fold_recall` 的返回正文）是同一问题的更严重版本：一次分段召回就可能取回几万字，而它是普通工具结果，原先整块平铺。现在同样按段收起，只有点开某一节才把那段正文挂进 DOM。

收起只解决「读多少」，不解决「多长」。三百多段的折叠原文收成三行一条的段清单后仍有一万来像素高，而它嵌在页面里：想滚到下面的内容，得先滚过整份清单。所以清单本身也要限高——段条目超过 20 条、目录行超过 40 行就装进固定高度的滚动框（`min(56vh, 560px)` / `min(38vh, 340px)`），页面高度只多一屏，不随段数增长；一屏以内不套壳，免得小折叠也白白多一层嵌套滚动。尾注（切分点、「还有 N 段没取回」）故意留在滚动框外：它们是要紧信息，不能被滚走。召回结果里的取回段清单同理，三种形态共用同一个判断。

这和插件的上下文折叠是两件事：插件折叠改的是模型收到的历史，UI 折叠只决定浏览器读多少、渲染多少。名字都叫「折叠」，所以页面上写清楚「点开一轮才读取并渲染正文」。
## 模型视角：为什么单独一个接口

账本页回答「赚不赚」，其中收支只吃 `fold-store` 的记录；模型视角回答「模型到底看到了什么」，必须读 `session.deriveMessages()`——检查点是否真的替换掉了原文、系统提示词与用户原话是否还在，只有派生消息能证明。

所以 `GET /fold-view?session=<id>`、`/fold-turn` 与 `/fold-composition` 共用 `buildReportModel`，但输出的是投影后的 JSON（`buildViewPayload`）：剥掉报告用的整段 `entry.text`，首包只留分组头、系统提示词（第 1 版要看全文）与重要消息；轮内条目和折叠原文由 `GET /fold-turn?session=<id>&ordinal=<组号>` 按轮取。两个接口都用同一份 `buildReportModel`，组号从 1 起、唯一，所以顺序对得上；会话在页面打开后又变过时，组号可能失效，按需接口会回 404 让页面提示刷新。两者都会随会话状态变化，因此都不落盘、不缓存。

## 召回留痕：标谁、怎么认

模型视角要回答「这段历史是怎么来的」，其中一条是「谁取回了哪段原文」。痕迹有两条通路：直接的工具调用（`fold_recall` 的参数是 JSON），以及宿主把工具包在代码执行器后面、真正的调用写在脚本里（`run_code` 的 `code` 字段）。只认 tool-call 名会漏掉后一条——而长会话里召回几乎都走代码执行器，漏掉就等于没有标记。所以两条通路都要认，且都从同一种原料出发：先解出调用参数，再扫。

扫描必须先解码再进入代码级判定，理由有两条。其一，`run_code` 的参数是一层 JSON，脚本里的引号与反斜杠都被转义，直接对原始参数做正则会把转义序列当成结构；解码之后 `code` 才是真正要读的代码。其二，代码里到处是字符串、模板与注释——日志摘录、文档示例、本插件自己的源码片段都会出现 `tools.fold_recall(` 字样。判定只在「代码位置」成立：跳过所有引号段与注释，调用必须写成 `tools.fold_recall({ ... })`，前面是分隔符、括号里第一个非空字符是对象字面量。宁可漏标，也不把示例点亮；标记一旦误报，用户就没法再信这张图。

计数向上传播，父级只做加法：条目记下自己的调用（直接调用逐次列出，折叠原文里的调用按次数汇总成「含召回 N 次」），分组把条目与折叠原文的调用相加，页面再把各分组相加；「被召回次数」来自召回流水按折叠编号聚合，挂在检查点上——召回取回的是原文，检查点本身没有被重发，标在条目上会误导。父级标签因此总能和子项对上，不需要另算一遍。

分段召回要标到具体段，但召回流水只记折叠编号、不记选了哪几段；能还原「取了哪几段」的原料是调用参数本身（`parts` 与 `query`），所以段级标记反过来从历史里的调用扫出来：先解出编号，再按与目录同一套规则切段（长回复按标题切段、检查点里回复没被截断时跳过回复段），用 `selectFoldParts` / `matchFoldPartNumbers` 求出这次碰到哪几段，最后挂到检查点对应的段上。解析结果同时回填到调用本身（`segments` / `segmentCount`）：界面上的 chip 直接写「召回 f4 · 段 #128」，而不是让读者自己拿 `parts: ["reply"]` 去对照结果里的段号。有工具结果时，回填的段号以结果正文为准：结果里实际返回了哪几段（`--- #N ---` 段头、目录里的 `#N [...]` 行）就标哪几段——参数写 195-207、结果只放下 #195 与 #196 时标的是两段，不是十三段。结果认不出表头时按失败处理，把第一行写成「未取回」的原因；整段召回与目录分别标「整段 N 段」「目录 29/207 段」，不把「只给了目录」读成「取回了这些段」。参数解析保留为兜底，只在这条调用没有结果正文（老数据）时使用；整段召回只报「整段」，不摊成上百个段标记，否则「被召回」会失去指向。段号是「此刻的段号」，配置改过 `maxRecallTokens` 后重建的段数可能与当时不同，这是可接受的偏差：标记回答的是「别处取的是哪一类内容」，不是审计级坐标。

段级标记同样是纯加法：段上的次数加起来是检查点的「段次」，各检查点的段次加起来是轮卡片的段次，再往上就是页头总额。段次与「被召回次数」不是一个量：一次调用可能取回五段，于是一个检查点 1 次召回、5 段次。界面上并排写，不合并成一个数。

标记还要落在「哪一段」上，而不只是「这条消息」。一条折叠段常常是「先思考、再调用」：段文本里两种标记都有，按块切成两段，调用属于后一段。早先按消息挂调用，两段就各带一串同样的 chip——表面上是重复，实际是标错了位置，读者会以为思考段自己发起了调用。现在折叠时按块记下每次调用出自第几个块（`recallCallBlocks`），页面按块切段时只把调用挂到那个块上；老载荷没有块归属时退回「调用块整条带走」，思考段仍然不标。宁可这一条调用少标一段，也不把标记撒到没发包的段上。

标记按方向分三种颜色：被召回红、召回黄、检索橘黄。早先两种标记都用冷色（靛蓝与青），在一屏几十个标签的清单里彼此分不开，也分不出方向——标记的作用是扫读，颜色分不开就等于没标。现在三者色相拉开，另加同色浅底、不透明文字与加粗：C.tag 默认是半透明的灰边小字，那种规格压在正文上会沉进去。颜色只管方向，不表示开销：账本页里「召回成本」的红色是数字不是标签，两处不在同一屏，不会混。

## 引用：从调用跳到段，从段跳回调用

标记只回答「有」，不回答「在哪」。一段折叠被十几个段取回、而取回它的调用又散在别的轮次里时，光有次数读者仍要自己翻页找位置。所以两边各存一份对方的落点，界面上互相可点：

- 调用这边：`foldLoc`（这条折叠的检查点在页面上的位置：组序号 `o` + 条目序号 `i`）加上结果里实际取回的段号。点 chip 打开面板，逐段列出可跳的落点。
- 被召回这边：检查点上的 `partRefs`（段号 -> 取回过它的调用落点，含轮号、折叠编号与 `part`）。点「被召回 N 次」打开面板，只列这一段自己的调用——从一段反查时把同一份折叠里别的段也列进来，读者会以为那些调用取的是这一段。

落点精确到段才算「跳到那次调用」。`o` 与 `i` 只把人送到条目：如果这次调用发生在某条折叠的原文里（已被折掉的调用），条目就是那条折叠的检查点——停在这里，读者还得自己展开原文、再逐段翻，才知道是哪一行调用了它。所以 `foldParts` 给每个段带上「出自第几个 item 的第几个块」，`attachPartRecalls` 据此算出每次调用在它所在折叠原文里的段号 `partNo`，引用行记成 `{o, i, part}`。两个下标与条目下发的 `blocks` 同序，也与召回目录的段号同一套规则（含长回复按标题切段），所以 part 就是页面上那一段的段号。

轮卡片上的合计标签（召回 / 被召回）同样可点：首包不带条目，所以点开时先按当前数据版本取那一轮的正文（`/fold-turn`，与面板预览共用缓存），再列成同一套条目。取数期间面板先显示「正在读取这一轮的正文…」；回调带一个世代号（`NAV.panelGen`），用户中途关掉或点了别的标签，迟到的结果不会把它顶掉。

落点只记数，不记 DOM 或文本：`o` 是分组序号（与 `/fold-view` 的分组一致）、`i` 是派生消息序号、`part` 是段号。页面按这几个数一路找到轮卡片、条目与段；展开时节点可能还没挂进 DOM（正文按需拉取、折叠原文按需渲染），所以跳转不是「滚到锚点」，而是一段逐层展开：轮卡片先 `open` 触发按需拉取，条目再展开，折叠原文面板再展开，最后把目标段 `open` 并滚到视口中间、短暂描边。每一层都靠 `details.open = true` 触发原生 `toggle`，复用已有的懒渲染路径，不另立一套「强制展开」状态。

面板只做「列去处」，点一条跳过去，跳完就关。它不复制原文——原文已经在页面里，再贴一份只会让两处对不上。但「段 #128」本身不是能记住的东西：面板里每条落点另带那一段的**开头一段**正文（约 120 字，去掉段头的 `[类型]` 前缀），从段反查调用时则把这一段自己的开头摆在面板顶部。预览按需取：面板一开才去读目标那一轮的条目（`/fold-turn`，按会话 + 轮次 + 数据版本缓存），同一轮只发一次请求，关掉再打开不重发；取不到时明写「没有取到这一段的正文」，不用段号冒充内容。

### 检索的引用指向分段目录

只给 `query` 的检索没有折叠编号，沿用不了「调用 → 这条折叠的第几段」那套落点。它真正用过的是每条命中折叠的**分段目录**：工具结果按折叠分组，写着「命中 14/151 段」，再列出命中的段号。所以检索的引用分两层——每条折叠一行「分段目录」，再逐段列出命中的段号；点目录一行落到那张目录，点段号落到那一段。段号与目录同一套规则，两边才对得上。

反方向也要留痕，否则「这张目录被谁用过」只能靠翻页找。`parseSearchHits` 从工具结果里解出命中的折叠与段号，`collectSearchHits` 把它们挂到被命中那条折叠的检查点上：`searchedParts`（段号 → 哪几次检索碰到它，带 `part` 以便落到那次调用）与 `searchedRefs`（哪次检索用到了这张目录、命中多少段）。这两张表**不并进** `partRefs` / `recalledParts`：检索没有返回原文，混进「取回 N 段次」会让取回量虚高。界面上它们用另一种措辞（「被检索」「检索×N」）与对应的橘黄，轮卡片与页头各自相加，父级仍然只做加法；一次检索同时命中同一轮里的两条折叠时，轮次标签按调用去重，否则「被检索 2 次」会被读成两次检索。命中的折叠不在这份历史里（载荷被清理、跨会话分叉）时只保留命中信息、不生成可点条目——跳不成比跳错好。

## 召回结果：按段折起来，切分点单独标

分段召回的返回是一整块工具结果正文，几万字铺进 DOM 既卡也看不出边界。但这段正文必须原样可读——它是模型真正收到的东西，模型视角页不能改写它。所以只在渲染层切：认表头（整段 / 分段 / 目录三种形态），分段形态按 `--- #N [类型] ---` 切成一节节折叠条目，收起时写「取回几段 / 哪几段（#195-#207）/ 多少字 / 几段被截断」；展开一节才挂正文。折叠原文面板里的分段目录同理：默认只留一行，点开才铺那几十行——目录是给「按段号选」用的索引，不是要一次读完的正文。

「单次不能全部获取」有两层含义，界面上分开标。其一，某段超过单次上限被裁剪：工具在段尾写了「本段已截断」，渲染时把正文切在那一行，换成一条切分点提示，写明原文多少字、这次返回前多少字——精确到字，不用 `7.3k` 这种约数，因为切分点是个坐标。其二，预算不够连段都放不下：工具在尾部写了「还有 N 段没取回」，渲染时单列成一条提示。尾注的识别有前提：只有「后面全是注释」的括号行才算尾注，正文里偶有一行以括号开头不会被当成截断。认不出表头时退回普通块原样显示，不猜。

## 上下文构成：折叠后与不折叠用同一把尺

用户要的不是「总共省了多少」（账本页已经回答），而是「省掉的是哪一类」。`lib/composition.js` 把每个分组按消息类型拆成八类：系统提示、旧版系统提示、用户原话、思考与回复、工具调用与结果、上下文注入、折叠摘要、重要消息。系统提示只认最后一条非空 `system/message`（宿主 `token-meter` 的 `contextBreakdown` 也是这么切的）。宿主换提示词时会在历史里 `append` 新的 `system/message`，但请求只把最后一条当生效提示，更早的版本留在 surface 里却不会上行——所以它们单列一类作参考，不计入合计与堆叠。

同一套分类要在两种视角下都能算，所以折叠后视角里检查点自成一类（它确实是模型看到的一块），不折叠视角里则把检查点的 `foldRecord.items` 逐块展开回原本类别——靠折叠时留下的载荷，不重读会话。

两条堆叠条共用一把尺：以不折叠的总量为满格，折叠后按总量比例缩短，条内色段仍按各自占比铺满。若两条都画成 100%，看上去像是总量相同、只是配色不同——长度差本身才是折叠省下的量。不折叠那条上另画一道竖线，标出「折叠后只保留到这里」，省下的部分一眼可见。

时间线是逐块累计（`cumulative`），回答的是「上下文怎样长起来、每次替换削掉哪一段」，不是当前快照。总量与每块增量两种模式共用同一份点数据，切换只决定读 `cumulative` 还是 `totals`。

面积只画当前视角，另一视角的累计总量用虚线叠在同一纵轴上（纵轴上限取两边的最大值）。这样切换视角时不必心算差额：两条线之间的高度就是折叠省下的部分，也省得把两个视角画成两张图再对比。

构成图与趋势图并排（`repeat(auto-fit, minmax(320px, 1fr))`，窄屏自动堆叠）：一张回答「省掉的是哪一类」，一张回答「省下的量怎么累积」，并排放才方便对照，也不会被拉成一整条横线。

## 构成图为什么单独一个接口

构成图画在账本页，但它的数据仍要从派生消息算。若账本每 20 秒去拉一次 `/fold-view`，一份长会话就是几 MB 的 JSON 白传一遍。所以单开 `GET /fold-composition?session=<id>`，只回 `buildComposition` 的结果：账本同时拉 `/fold-stats`（5 秒，只读记录）与 `/fold-composition`（20 秒，要派生消息），互不牵制。模型视角页不再画构成图，它只回答「模型看到了什么」。

## 设置页：字段表只有一个来源

参数表单挂在原生「插件」页的组合包配置位（`plugins.bundle.config`，key 是组合包名 `dsh-fold-context`），不再占着对话顶栏：顶栏是「这个会话怎么样」，插件页才是「这个插件怎么配」。插件管理页用注册项的 `key` 判断该组合包有没有配置区，所以 key 必须与包名一致；没有 `ui-plugin-manager` 的部署里这块不渲染，`fold_config` 工具照旧可用。

`configFields()` 同时喂三个出口：`fold_config` 工具的说明、`GET /fold-config` 的表单、`validateConfigPatch` 的校验。新增字段只改 `lib/config.js` 的 `FIELDS`，三处自动跟上，不会出现「工具能改、页面不认」的漂移。

保存走和 `fold_config set` 同一条严格校验：未知键、类型错、越界、字符串超长整批拒绝，页面把错误原文显示出来。校验通过后先热更新内存并重建系统提示段，宿主没接线 `updateConfig` 时才退回只写文件。
