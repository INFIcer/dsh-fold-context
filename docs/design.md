# 设计说明

## 为什么是「替换」而不是「改写请求」

DSH 的模型可见内容必须能从会话日志重建，所以插件不改模型请求，而是往 surface 上写一条真正的事件。
折叠 = `session.append('user/message', 检查点, { surfaceOp: { op: 'replace', startSeq, endSeq }, sourceEventSeqs })`。
这条事件遮蔽了本轮原有的节点，`deriveMessages()` 立刻反映新历史；重启后 seed 重放同一套校验，不需要任何迁移代码。

只写内置的 5 种 surface 类型之一，不自造事件类型，也不注册 message projection——插件卸载后旧会话仍然可读，只是检查点退化成普通的 user 消息。

## 切点为什么按「轮」而不是按 token

折叠的收益是前缀稳定：整轮替换后，下一次请求只在一个位置发生变化，前缀缓存最多失效一段，而不是被切碎成多处。
按 token 压缩需要预测哪些内容不再被用到，猜错的成本是模型失去依据；按轮折叠把预测推迟到召回时——召回是模型主动发起的，它比任何静态策略都清楚自己缺什么。

## 折叠粒度

片段从第一条非保留节点开始，包含它全部的 `tool/result`，遇到保留节点（用户原话、重要消息、上一次的检查点）就断开。
这样折叠区间总是落在整步上，不会把一次调用和它的结果切开，也不会让一个未完成的步骤消失；落单的 `tool/result` 直接跳过。
一轮开头的上下文注入与调度提醒属于这一轮的上下文，跟着片段一起折。它们是 agent-loop 每轮重新生成的快照，折掉不会失去能力：下一轮会重新注入最新的一份，旧版本仍可 `fold_recall` 取回。系统提示词不是 `user/message`，从不进入折叠区间。
同一轮里如果用户插话或模型发了重要消息，片段会被切成多段，每段各自替换成一条检查点。

## 可调参数与运行时配置

折叠力度不该写死在代码里：同一套阈值在短会话里折得太碎，在长会话里又太粗。参数集中到 `lib/config.js` 的 `FIELDS`，字段白名单只有这一处，默认值、类型、范围、说明都从这里生成。

配置分三层：默认值 < profile 里的 `config` < `$DSH_HOME/fold-config.json`。文件放在最后，是为了让人手工改文件能压过 profile 里的旧值。

两条校验路径刻意不同：

- 加载时钳制：`normalizeConfig` 把越界数字夹回区间、类型不对就保留基线值、未知键忽略并 `warn`。目标是「配置写坏也能起」。
- 运行时修改严格拒绝：`validateConfigPatch` 对 `fold_config` 的 patch 逐项检查，未知键、类型错、越界、字符串超长都返回原因，整批不生效。目标是「模型不会误以为改成功了」。

### 摘要预算：noteRatio 与 maxNoteChars

检查点摘要的长度是两层约束：`min(maxNoteChars, max(80, round(原文 * noteRatio)))`。先按比例给预算，再压在硬上限之下；80 是下限，保证编号与召回入口总写得进去。

按比例而不是按固定字数，是因为折叠的对象本身长短差很多：一段 800 字的思考和一段 8000 字的工具往返，用同一个 320 字上限，前者浪费预算、后者信息密度不够。默认 `noteRatio=0.1` 让 3200 字左右的轮次刚好贴着 320 的上限，和旧行为接近。

### 工具输出要不要折：foldToolOutputs

默认 `true`。设成 `false` 时工具输出不进摘要、不进召回载荷，也不计入 `minFoldChars` 的体量——三者必须一致，否则会出现「摘要说折了、召回却拿不到」的错位。适合工具输出另有日志可查、只想折叠思考与回复的场景。

### 每轮折几段：maxFoldsPerTurn

同一轮里用户插话或模型发重要消息会把片段切成多段。每段都是一次 surface replace，都会让下一次请求的前缀变化一次；默认 8 段是上限，超出的片段保留原文，宁可少折也不让前缀抖成筛子。

### 文案与排序

`systemPromptText` 可整段替换提示词，支持 `{{recallTool}}`、`{{pinTool}}`、`{{configTool}}`、`{{ratio}}`；`recallReminderText` 控制召回超阈值时的提醒，支持 `{count}`、`{tool}`。占位符都是字面替换，不认识的占位原样保留，不会因为配置里多写了一个占位就整段消失。`promptOrder` 决定提示段插在哪，默认 300。

### fold_config：运行时读写

`fold_config` 有三个动作：`get` 返回当前生效配置、文件路径与每项范围；`set` 收一个白名单 patch；`reset` 恢复默认值。`set`/`reset` 先整份写入 `<home>/fold-config.json`，再调用宿主注入的 `updateConfig(patch)` 立即生效。写文件失败则不热更新，避免内存与磁盘不一致；宿主没接线 `updateConfig` 时只落盘，并在返回值里明确说「重启后生效」。

## 触发点

`agent/turn-stopping` 是轮即将关闭、`turn/end` 尚未落盘的串行钩子：此时不在任何 append 的发布临界区，可以同步写；`turn/end` 时本轮内容还没散，节点也齐全。
作为兜底，`session/event` 观察到 `turn/end` 时在 `setImmediate` 之后补一次（观察者内同步 append 会撞上重入禁令）；已经折过的轮子再折一次是空操作，因为检查点本身属于「不折」的那一类。

## 重要的信息为什么能不被折

折叠是机械规则，它不理解语义，所以判断「什么日后还会用到」交给模型，插件只提供落点与压力：

- 软性：系统提示词告诉模型，需要跨轮复用的事实应该用 `fold_pin` 固化。
- 客观指标：召回次数会累加，超过阈值时工具返回里直接要求「这条已被召回 N 次，把可复用的结论固化下来」。
- 用户可以直接说哪些内容要留，模型据此调用 `fold_pin`。

不追求一次判断准确：召回本身就是事后评估，判断错了下一轮还能补。

## 与压缩引擎的关系

插件不碰 `compaction/*` 事件，也不参与摘要生成，只在原来的压缩引擎之外做「低增速」这一层。
两者可以并存：折叠管日常增速，compaction 管真正的超限清理。

### token 口径

账本、模型视角与逐轮报告现在用同一把尺：每个内容块 `ceil(字符数 / 4) + 4`，工具调用的名字与参数各算一块，每条消息再加 4。这是宿主 token-meter 与侧栏「上下文」页（dsh-context）共用的经验公式，不是分词器。

报告早先给两档（3.2 与 1.6 字符/token），本意是「中英之间给个区间」，结果是同一条历史在账本与报告里出现三个不同的数，用户第一反应是算错了。区间看似诚实，实际只是把不确定性摊在界面上；既然宿主已有唯一口径，就该跟它对齐。

我们的数字只覆盖折叠产物，不含系统提示词与工具定义，所以和「上下文」页的总占用不可直接比；对照时要么补上那两项，要么只看同一批消息的增量。

### 外部压缩代理

billion-context 在请求侧重写历史，不写 DSH 会话日志，也不读 `surfaceOp`；本插件在日志侧做替换。两者互不破坏，但代理会把压缩块范围内的检查点与 `fold_pin` 一起摘要掉——「永不折叠」只在本插件的表层成立。

因此检查点正文必须带 fold 编号：编号落在代理摘要里也还能用 `fold_recall` 从本地 `fold-store` 取回原文。若要 pin 在代理层之上也常驻，只能把内容注入系统提示词（`PromptSection.text` 支持函数形态），代价是每次 pin 变化都让前缀缓存失效一次；v1 选择不做，保持「pin 是历史里的一条消息」这个可解释的语义。
## 顶栏账本：折叠是收益，召回与固化是成本

折叠本身有代价（下次请求前缀变化、摘要占位），只喊「省了」没有意义，所以顶栏那页把两边都摆出来：绿条是折叠省下的 token，红条是这一轮召回和重要消息的开销。

### 为什么数据不从 deriveMessages 来

逐轮报告（`GET /fold-report`）能拿到 `session.deriveMessages()`，所以它按模型真实视角逐条重建。顶栏路由不一样：它是无状态的 HTTP 请求，手里只有会话 id，而且每 5 秒被调一次——把会话拉起来、重建派生消息、再算 token，成本远高于它展示的数字本身。

因此 `lib/stats.js` 只吃 `fold-store` 的记录：折叠记录里已经写了原文总字符、摘要和逐条载荷，召回记录写了返回大小，重要消息记录写了正文。这些都是写入时的事实，不需要重新读会话。

代价是「折叠后真实占用」只能近似：页面显示的是折叠摘要与重要消息的 token 之和，不含其它历史。够用，因为这一页回答的是「这套机制到底赚不赚」，不是「当前上下文精确有多少」。

### 口径与宿主一致

`lib/tokens.js` 复刻 `dsh-token-meter` 的估算：每 4 字符 1 token，每个文本块再加 4 token（`BLOCK_OVERHEAD`）。折叠收益 = 载荷逐块的 token 和 − 摘要那一块的 token；召回成本 = 当时返回正文的 token；重要消息成本 = 它作为一条消息的 token。同一段文本在两处计算会得到同一个数，页脚也写明这一点，避免和宿主自己的用量对不上时怀疑数据错。

### 轮次归属与旧记录

新写的召回记录带 `turn`、正文字数与 token；重要消息记录带 `turn`。老记录没有这些字段，统计时退回到「按被召回折叠所在的轮」估算，并在界面上标 `estimated`。这样升级插件不会让历史数据消失，也不会假装精确。

### 为什么是轮询而不是 SSE

数据是几十条记录聚合出来的小 JSON，5 秒一拉足够。SSE 要维护连接、处理重连、在宿主侧保存订阅者，收益只是更实时——而折叠发生在轮末，本来就是分钟级的节奏。将来若要更实时，可以在 `foldTurn` 成功后向订阅者推一条事件，接口形状不用变。

### 请求开销：为什么按轮重放

账本原来的「收益」只比了末态大小，这解释不了「折叠到底省了多少次重复发送」。真实开销发生在每一次请求上：同一个前缀被重发 k 次，命中缓存的部分和未命中的部分价格不同。

因此 `lib/cost.js` 把两种历史各重放一遍。折叠后的视角用「累计历史 + 上一轮检查点」当本轮请求内容，不折叠的视角用「累计原文」；重放量按 `k × 前缀 + 新增 × (k−1)/2` 算，再按命中率拆成命中与未命中两档计价。两个关键点：

- 检查点只在下一轮发一次，本轮自己的检查点不计入本轮请求（它写在轮末）。
- 折叠改写了前缀，上一轮检查点在本轮首请求是未命中的；命中只从更早、已缓存的内容算起。没折叠的短回合整段仍是新内容，不会虚增节省。

`cacheHitRate` 是「前缀里有多少真的命中了缓存」，默认 0.97（DeepSeek 实测值），而不是「缓存价是输入价的几分之一」。这个区分是踩过坑的：早先把 0.25 当成命中比例，看上去保守，实际却把 98% 本该计费的前缀压到 2% 按命中价、其余按 0 元——账单只有真账的三分之一。

光有重放还不够。请求期压缩器（如 billion-context）会在发出前再收缩一次上下文，所以按 surface 重放出来的 token 系统性大于 provider 计费量（本会话实测约 2.4 倍，而每步的比值还随轮次从 0.32 漂到 0.70）。因此模型里留了一个反推步骤：拿到过 usage 就用实测总量反推 `promptScale`、`outputScale` 与实测命中率，再把系数套回全部轮次。估算是被实测钉住的，不是靠人调一个「看起来差不多」的折扣。

### 收益为什么用 token 计，金额只作折算

折叠的收益是「这些 token 没有被重发」，它不该折成人民币当收益：同一批 token 换成高峰价就翻倍，真实请求还会被缓存命中率、请求期压缩器和工具定义改写，最后算出来的钱既无法验证、也无法跨会话比较。所以账本顶部的收益与成本一律报 token，读数能直接对到上下文本身。

金额只回答另一个问题：「这些 token 按当前单价折算是多少」。它出现在成本参考的表格与「实测账单」里，用来和 provider 的计费对账。为了让对账成立，折算要分三档，因为三档 token 的价格差上百倍（空闲时段命中 0.02、未命中 1、输出 4，元 / 百万 token）。`lib/cost.js` 每轮同时给出 `foldedHitTokens` 与 `foldedInputTokens`（不折叠视角同理），`lib/pricing.js` 再把它们各乘自己那档单价。

输出单独记是因为它不该参与「折叠省了多少」的比较——同一句回复折与不折都要生成一遍，做差必然为零。把它列进参考，是为了让参考值和 provider 回报的三档数字能逐项对上；如果只算输入，参考值会永远比实测小一截，看起来像估算失败。

单价是可配的，因为官方价会变、用户也可能用别的模型跑同一个会话（缓存命中价与输出价的倍率各家不同）。默认值取 DeepSeek 2026-11 的官方价目表（空闲时段；高峰是这套的两倍）；改单价只影响结算，不影响 token 估算本身，也不触发任何历史重算——账本每次请求都按当前单价现算。

### 实际请求为什么单独显示

估算量的是会话历史，provider 回报的是真正上行的 token。billion-context 这类代理在请求期又压缩了一次，两边的差可能很大（本会话实测过估算 37 万、provider 回报 8 万）。差不是估算算错了，是两句话口径不同，所以 `cost.drift` 把它拆成三段：

- `governedTokens`：归折叠管的部分，即插件生效后的历史加当前系统提示。这一段能和实测并排比。
- `legacyTokens`：插件生效前的那一轮，插件永远折不动它，实测里它已被请求期压缩器改写。把它单列，估算就不会看起来系统性偏高。
- `externalTokens`：实测减去 governed 的余量，来自历史之外——工具定义、请求期压缩器注入的摘要。

比调低估算系数诚实：估算不参与反事实推算，只当 ground truth；拆口径只改解释，不改账。

一开始这个差还有一半是我们的错：surface 里留着 6 份历史版本的系统提示词，统计时全算了进去，光这一项就多出十几万 token。宿主只把最后一条 `system` 当生效提示，于是 `excludeStaleSystem`（`lib/inspect.js`）把更早的版本从「模型视角」总量里扣掉，`lib/composition.js` 把它们标成 `reference` 只展示不计入，`lib/cost.js` 也只累加当前那条。另一半差额来自请求期压缩器，这部分不在本插件能看到的数据里。

### 客户端为什么手写

DSH 的客户端插件产物就是 `window.__ModuleLoader__.load({ id, factory })` 包住的 CJS，`require("react")` 由宿主给。这个页面只有一个 Tab、一张图表和两张表，引入 tsdown/vite 构建链只会让「改一行要重新打包」成为障碍；手写 `client/client.js` 后，改完刷新页面就生效。

## 逐轮视图：为什么这样分组

报告的主视图是「一轮一个 `<details>`，收起时只露用户原话与回复」。分组规则不是随手定的：

- **按用户消息切轮**：用户消息是人与模型共同的锚点，也是折叠规则里唯一「永不折叠」的类别，用它开一轮，报告的边界和折叠的边界就是同一个。
- **系统提示词就地成块**：`system/message` 会出现在历史中间（宿主换提示词或插件重建提示段时追加），它属于「那个时刻」，不属于某一轮。所以它就地开一个 system 组、同时切断当前轮：出现在轮与轮之间就夹在两轮之间，出现在轮中就把那一轮切成前后两半。代价比「整体抽到最前」小：抽到最前会让时间顺序失真，也没法表达「第 2 版提示词之后模型看到的历史变了」。
- **`schedule` 投递的消息算用户消息**：调度器发来的是用户指令，折掉等于吞掉用户要求，所以它和 `user` 走同一条「不折」分支。
- **检查点归上一轮**：一条检查点表达的就是「这一轮被折成了这样」，它是轮的结尾而不是下一轮的开头。
- **轮次号按顺序数，不用记录里的 `turn`**：记录里的 `turn` 是宿主进程内的计数器，重启后从 1 重来，拿它当全局轮号会串号。现在按用户消息出现的位置编号 1..N；第一次出现折叠记录之前、又没有折叠的轮标「插件生效前·未折叠」，没折叠且内容很少的标「内容较少·未折叠」。

## 为什么正文不截断

旧版为了控制报告体积，把每条消息压成 200 字预览加省略号。结果系统提示词（八万字）、用户原话、插件装上之前的那一轮，看上去都像被折叠或截断了——报告的显示方式被误读成了折叠的实际行为，而折叠本身没有任何问题。

现在所有正文完整渲染，长文本只加 `max-height` 滚动框，工具栏的「展开长文本」可以去掉高度限制。宁可文件大一点，也不让「没折叠」在视觉上像「折叠了」。

## 底色而不是字色

只改文字颜色，在几万字的报告里几乎看不出差别；折叠摘要与原文还都是灰底正文，更容易混。现在按消息类型给整块背景色：用户原话蓝、注入灰、检查点蓝灰、思考琥珀、调用靛、结果橙、回复绿、重要消息紫。摘要块带一条「以下是折叠掉的原文，报告替你摊开，模型看不到」的分隔线——颜色告诉眼睛这是什么，分隔线告诉它模型看不看得到。

## 在线入口与离线脚本

报告只有一个在线入口：`GET /fold-report?session=<id>`。服务端按会话 id 找到活着的会话，当场算、当场回 HTML，不落盘；顶栏「折叠」页的「逐轮报告」按钮就是打开它。插件不再向模型暴露报告工具——报告是给人看的，放进工具表只会多占一份 schema。

宿主不在时用 `tools/render-report.mjs`：自己解多帧 zstd 会话日志、按 `surfaceOp` 重放 surface、再从节点派生消息，走的是和宿主同一套规则（`append` 推入、`replace` 用 `splice(start, end - start + 1, seq)` 覆盖）。所以离线报告与在线报告的「模型视角」应当逐条一致，不一致就说明重放逻辑或插件写的区间有问题。

## 分级召回：为什么先给目录

一段折叠原文可能是几十万字：思考、工具调用参数、工具输出全在里面。整段塞回上下文，既贵又淹没有用信息——模型真正需要的往往只是其中一两段。

所以 `fold_recall` 按体量分两档：

- 原文不超过 `recallDirectChars`（默认 8000 字）：直接返回全文，保持旧行为，模型不用多调一次。
- 更长：先返回分段目录——每段一行「#3 [工具结果] 1,234 字：开头预览」，外加类型统计与合计。模型看完目录，再用 `parts` 选段：`["1", "4-6"]` 选段号与区间，`["think"]` / `["tools"]` / `["reply"]` 选类型，`["all"]` 全要。一次可以多选，选中的段按段号升序拼回去。

分段单位不是「一条节点」而是「一个内容块」：同一条 assistant 消息里的思考、回复、工具调用各自成段，工具结果单独成段。这样模型能只要思考、不要工具输出。段号在一次折叠内连续，跨节点不重来，模型只需要记 `#3` 这种短编号。

目录本身也受 `maxRecallChars` 约束：超了就按行截断，并明确说还有多少段、建议用哪个区间选。只查目录不增加「内容召回」计数——否则模型每看一眼目录就被提醒去固化，压力会失真。

## 模型视角：为什么这样排

模型视角页回答的是「模型此刻到底看到了什么」，所以它的顺序必须等于派生消息的顺序，不能为了好看重排：

- **重要消息按时间顺序贴在轮次之后**：这一页的职责是复现模型看到的历史顺序。抽到页顶就成了一份摘要，读者会以为约束是后加的；贴在出现位置之后，才看得出「这条约束是在第几轮、看到什么之后立下的」。轮卡片头部的紫色 chip 负责扫读。
- **系统提示词按出现时间成块**：提示词换版是历史事件，第 2 版之后模型看到的世界变了；把它抽到最前，就等于假装整个会话都在用最后一版。
- **第 2 版起默认只看差异**：两版提示词动辄七八万字，逐版全文铺开既占体积也看不出改了什么。`lib/diff.js` 剥掉公共前后缀再做 LCS，只给改动区间加两行上下文；`maxCells` 与 `maxDiffLines` 兜住极端输入，超预算就退化成「整段删除 + 新增」或直接标 `truncated`。
- **第 1 版必须给全文**：没有前一版就没有差异可看，而第 1 版恰恰是模型自我认识的全部依据。

## UI 折叠：为什么不是渲染完再隐藏

一份长会话的模型视角有一百多万字。`<details>` 收起时内容仍在 DOM 里，浏览器照样要解析、排版、占内存，用户看到的就是点开这页先卡两秒。

所以卡片收起时根本不挂正文：`useLazyOpen()` 用 `onToggle` 读 `event.currentTarget.open`，关着就返回空 body。折叠掉的原文同理，每段一个独立的 `<details>`，展开一段才渲染一段——二百多段的旧轮次也不会一次摊开。

这和插件的上下文折叠是两件事：插件折叠改的是模型收到的历史，UI 折叠只决定浏览器渲染多少。名字都叫「折叠」，所以页面上写清楚「点开一轮才渲染正文」。
## 模型视角：为什么单独一个接口

账本页回答「赚不赚」，其中收支只吃 `fold-store` 的记录；模型视角回答「模型到底看到了什么」，必须读 `session.deriveMessages()`——检查点是否真的替换掉了原文、系统提示词与用户原话是否还在，只有派生消息能证明。

所以 `GET /fold-view?session=<id>` 与 `/fold-report` 共用 `buildReportModel`，但输出的是投影后的 JSON（`buildViewPayload`）：剥掉报告用的整段 `entry.text`，只留渲染需要的块与折叠载荷预览。两者都会随会话状态变化，因此都不落盘、不缓存。

## 上下文构成：折叠后与不折叠用同一把尺

用户要的不是「总共省了多少」（账本页已经回答），而是「省掉的是哪一类」。`lib/composition.js` 把每个分组按消息类型拆成八类：系统提示、旧版系统提示、用户原话、思考与回复、工具调用与结果、上下文注入、折叠摘要、重要消息。系统提示只认最后一条非空 `system/message`（宿主 `token-meter` 的 `contextBreakdown` 也是这么切的）。宿主换提示词时会在历史里 `append` 新的 `system/message`，但请求只把最后一条当生效提示，更早的版本留在 surface 里却不会上行——所以它们单列一类作参考，不计入合计与堆叠。

同一套分类要在两种视角下都能算，所以折叠后视角里检查点自成一类（它确实是模型看到的一块），不折叠视角里则把检查点的 `foldRecord.items` 逐块展开回原本类别——靠折叠时留下的载荷，不重读会话。

两条堆叠条共用一把尺：以不折叠的总量为满格，折叠后按总量比例缩短，条内色段仍按各自占比铺满。若两条都画成 100%，看上去像是总量相同、只是配色不同——长度差本身才是折叠省下的量。不折叠那条上另画一道竖线，标出「折叠后只保留到这里」，省下的部分一眼可见。

时间线是逐块累计（`cumulative`），回答的是「上下文怎样长起来、每次替换削掉哪一段」，不是当前快照。总量与每块增量两种模式共用同一份点数据，切换只决定读 `cumulative` 还是 `totals`。

面积只画当前视角，另一视角的累计总量用虚线叠在同一纵轴上（纵轴上限取两边的最大值）。这样切换视角时不必心算差额：两条线之间的高度就是折叠省下的部分，也省得把两个视角画成两张图再对比。

构成图与趋势图并排（`repeat(auto-fit, minmax(320px, 1fr))`，窄屏自动堆叠）：一张回答「省掉的是哪一类」，一张回答「省下的量怎么累积」，并排放才方便对照，也不会被拉成一整条横线。

## 构成图为什么单独一个接口

构成图画在账本页，但它的数据仍要从派生消息算。若账本每 20 秒去拉一次 `/fold-view`，一份长会话就是几 MB 的 JSON 白传一遍。所以单开 `GET /fold-composition?session=<id>`，只回 `buildComposition` 的结果：账本同时拉 `/fold-stats`（5 秒，只读记录）与 `/fold-composition`（20 秒，要派生消息），互不牵制。模型视角页不再画构成图，它只回答「模型看到了什么」。

## 设置页：字段表只有一个来源

参数表单挂在原生「插件」页的组合包配置位（`plugins.bundle.config`，key 是组合包名 `dsh-fold-plugin`），不再占着对话顶栏：顶栏是「这个会话怎么样」，插件页才是「这个插件怎么配」。插件管理页用注册项的 `key` 判断该组合包有没有配置区，所以 key 必须与包名一致；没有 `ui-plugin-manager` 的部署里这块不渲染，`fold_config` 工具照旧可用。

`configFields()` 同时喂三个出口：`fold_config` 工具的说明、`GET /fold-config` 的表单、`validateConfigPatch` 的校验。新增字段只改 `lib/config.js` 的 `FIELDS`，三处自动跟上，不会出现「工具能改、页面不认」的漂移。

保存走和 `fold_config set` 同一条严格校验：未知键、类型错、越界、字符串超长整批拒绝，页面把错误原文显示出来。校验通过后先热更新内存并重建系统提示段，宿主没接线 `updateConfig` 时才退回只写文件。
