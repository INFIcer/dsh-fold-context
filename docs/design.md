# 设计说明

## 为什么是「替换」而不是「改写请求」

DSH 的模型可见内容必须能从会话日志重建，所以插件不改模型请求，而是往 surface 上写一条真正的事件。
折叠 = `session.append('user/message', 检查点, { surfaceOp: { op: 'replace', startSeq, endSeq }, sourceEventSeqs })`。
这条事件遮蔽了本轮原有的节点，`deriveMessages()` 立刻反映新历史；重启后 seed 重放同一套校验，不需要任何迁移代码。

只写内置的 5 种 surface 类型之一，不自造事件类型，也不注册 message projection——插件卸载后旧会话仍然可读，只是检查点退化成普通的 user 消息。

## 切点为什么按「轮」而不是按 token

折叠的收益是前缀稳定：整轮替换后，下一次请求只在一个位置发生变化，前缀缓存最多失效一段，而不是被切碎成多处。
按 token 压缩需要预测哪些内容不再被用到，猜错的成本是模型失去依据；按轮折叠把预测推迟到召回时——召回是模型主动发起的，它比任何静态策略都清楚自己缺什么。

## 折叠粒度

片段必须从 `assistant/message` 开始，包含它全部的 `tool/result`，遇到 `user/message` 就断开。
这样折叠区间总是落在「一次完整的思考 + 它的工具往返」上，不会把一次调用和它的结果切开，也不会让一个未完成的步骤消失。
同一轮里如果用户插话或模型发了重要消息，片段会被切成多段，每段各自替换成一条检查点。

## 可调参数与运行时配置

折叠力度不该写死在代码里：同一套阈值在短会话里折得太碎，在长会话里又太粗。参数集中到 `lib/config.js` 的 `FIELDS`，字段白名单只有这一处，默认值、类型、范围、说明都从这里生成。

配置分三层：默认值 < profile 里的 `config` < `$DSH_HOME/fold-config.json`。文件放在最后，是为了让人手工改文件能压过 profile 里的旧值。

两条校验路径刻意不同：

- 加载时钳制：`normalizeConfig` 把越界数字夹回区间、类型不对就保留基线值、未知键忽略并 `warn`。目标是「配置写坏也能起」。
- 运行时修改严格拒绝：`validateConfigPatch` 对 `fold_config` 的 patch 逐项检查，未知键、类型错、越界、字符串超长都返回原因，整批不生效。目标是「模型不会误以为改成功了」。

### 摘要预算：noteRatio 与 maxNoteChars

检查点摘要的长度是两层约束：`min(maxNoteChars, max(80, round(原文 * noteRatio)))`。先按比例给预算，再压在硬上限之下；80 是下限，保证编号与召回入口总写得进去。

按比例而不是按固定字数，是因为折叠的对象本身长短差很多：一段 800 字的思考和一段 8000 字的工具往返，用同一个 320 字上限，前者浪费预算、后者信息密度不够。默认 `noteRatio=0.1` 让 3200 字左右的轮次刚好贴着 320 的上限，和旧行为接近。

### 工具输出要不要折：foldToolOutputs

默认 `true`。设成 `false` 时工具输出不进摘要、不进召回载荷，也不计入 `minFoldChars` 的体量——三者必须一致，否则会出现「摘要说折了、召回却拿不到」的错位。适合工具输出另有日志可查、只想折叠思考与回复的场景。

### 每轮折几段：maxFoldsPerTurn

同一轮里用户插话或模型发重要消息会把片段切成多段。每段都是一次 surface replace，都会让下一次请求的前缀变化一次；默认 8 段是上限，超出的片段保留原文，宁可少折也不让前缀抖成筛子。

### 文案与排序

`systemPromptText` 可整段替换提示词，支持 `{{recallTool}}`、`{{pinTool}}`、`{{configTool}}`、`{{ratio}}`；`recallReminderText` 控制召回超阈值时的提醒，支持 `{count}`、`{tool}`。占位符都是字面替换，不认识的占位原样保留，不会因为配置里多写了一个占位就整段消失。`promptOrder` 决定提示段插在哪，默认 300。

### fold_config：运行时读写

`fold_config` 有三个动作：`get` 返回当前生效配置、文件路径与每项范围；`set` 收一个白名单 patch；`reset` 恢复默认值。`set`/`reset` 先整份写入 `<home>/fold-config.json`，再调用宿主注入的 `updateConfig(patch)` 立即生效。写文件失败则不热更新，避免内存与磁盘不一致；宿主没接线 `updateConfig` 时只落盘，并在返回值里明确说「重启后生效」。

## 触发点

`agent/turn-stopping` 是轮即将关闭、`turn/end` 尚未落盘的串行钩子：此时不在任何 append 的发布临界区，可以同步写；`turn/end` 时本轮内容还没散，节点也齐全。
作为兜底，`session/event` 观察到 `turn/end` 时在 `setImmediate` 之后补一次（观察者内同步 append 会撞上重入禁令）；已经折过的轮子再折一次是空操作，因为检查点本身属于「不折」的那一类。

## 重要的信息为什么能不被折

折叠是机械规则，它不理解语义，所以判断「什么日后还会用到」交给模型，插件只提供落点与压力：

- 软性：系统提示词告诉模型，需要跨轮复用的事实应该用 `fold_pin` 固化。
- 客观指标：召回次数会累加，超过阈值时工具返回里直接要求「这条已被召回 N 次，把可复用的结论固化下来」。
- 用户可以直接说哪些内容要留，模型据此调用 `fold_pin`。

不追求一次判断准确：召回本身就是事后评估，判断错了下一轮还能补。

## 与压缩引擎的关系

插件不碰 `compaction/*` 事件，也不参与摘要生成，只在原来的压缩引擎之外做「低增速」这一层。
两者可以并存：折叠管日常增速，compaction 管真正的超限清理。
