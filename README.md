# dsh-fold-context

按轮折叠 DSH 会话历史：每轮结束时把本轮的思考、工具输出与长回复折成一条检查点消息，原文可凭编号召回，重要的结论由模型按需固化成常驻消息。

它不接管压缩引擎，只降低每轮历史进入上下文的速度。

## 行为

1. 轮结束（`agent/turn-stopping`）时，把本轮从第一条非保留消息到最后一个节点的区间整体替换成一条 `user/message` 检查点消息。
2. 不折：真正的用户原话、调度器投递的用户指令、`fold_pin` 重要消息、上一次的检查点本身、`system/message`，以及全部上下文注入（审批变化、子代理通知、工具变更、模型切换、运行时快照、时间上下文、技能目录等）；折不折按比例判断——检查点长度低于原文的 `minFoldRatio` 倍（默认 0.5，至少省一半）才折，否则保留原文；没有单独的「轮次太小不折」阈值，小轮次同样按比例算。注入一概保留：一次性注入宿主不会补发，折掉就永久丢失；会重放的那几种，宿主按「消息还在不在可见历史里」决定要不要再发一份，折掉省下的量会被完整重发抵消（技能目录重发的还是全量）。真正被折的只有思考、工具输出与长回复。
3. 检查点正文写清折叠了几步、几次工具调用、工具名、回复的开头与结尾（markdown 回复按标题摘要，见第 4 条），并给出 `fold_recall("f7")` 这类编号；另有一行「· 文件：改过 …；读过 …」记下这一轮碰过哪些文件——改过的要重读，只读过的不必整份重读。
4. 召回是分级的：`fold_recall("f7")` 先算分段目录（段号、类型、字数、开头——每行在预览与原文之间取更短的一种，预览不比原文短就直接给原文），目录整体省不到原文的 `minFoldRatio` 倍时直接返回原文、不做两级召回；否则给目录，模型再用 `fold_recall("f7", parts: ["1", "4-6"])` 或 `parts: ["think"]` / `["tools"]` 多选取回。超过一次召回额度的长 markdown 回复还会按标题切成独立段，短回复仍整段返回。内容召回会累计次数，超过 `recallReminderAfter` 时要求模型用 `fold_pin` 固化结论；只查目录不算。载荷在折叠时就保存整段原文（含最终回复与完整的工具调用参数），召回限流只发生在返回时；载荷按会话受 `maxStoreTokens` token 约束，超了先清理最旧的折叠。
5. 只记得关键词时用检索：`fold_recall({query: "lib/web.js"})` 扫全部折叠原文，只回折叠编号、段号与命中片段，不返回原文，也不计召回次数；拿到编号后再 `fold_recall({id: "f5", parts: ["2","4"]})` 取原文。`id` 与 `query` 同时给时，只在这条折叠里筛段。
6. `fold_pin` 追加一条 `【重要·永不折叠】 标题` 消息：本插件的按轮折叠不会折它；长会话里压缩层仍可能随时间把它并进摘要，插件不补发。发布时可以标 `level`：省略或 `"permanent"` 是长期重要，消息头是 `【重要·永不折叠】 标题`；`"recent"` 表示近期重要、可能过时（临时但可能跨轮用），消息头是 `【近期重要·第N轮·可能过时】 标题`，N 是发布时的会话轮次，与检查点「第 N 轮已折叠」同一个计数口径。recent 不自动过期、不改写已注入的消息，跨几轮后由模型用前核实或重读来源；两个值以外一律不发布。账本按「模型此刻看得见的那几条」计价：核对活会话里的历史，被卷走的标成 `present: false` 只报体积、不进成本；反过来，上下文里还在、载荷里已无记录的也按字数计价（卡片会写「其中 N 条账本没有记录」）。拿不到活会话时保持旧口径（按载荷记录算）。默认不设条数与长度上限：值不值得记交给模型判断，`maxPins` 与 `pinBudgetTokens` 只有在显式设成正数时才作为软上限提示，不会拒绝发布。
7. 系统提示词追加一段 `fold-compression`，说明机制与三个工具（`fold_recall`、`fold_pin`、`fold_config`）的用法。
8. 模型可以用 `fold_config` 在会话中查看、修改或重置配置，不用重启。
9. 折叠按会话启用：`foldSubagents` 默认 `false`，只在主会话折叠；子代理（含 fork）的轮次保持原文。子代理只得到一段短提示——本会话不折叠，`fold_pin` 记下的重要消息只有自己看得见；普通子代理没有 `fold_recall` / `fold_config`，fork 子会话因为历史里有父会话的检查点，再多一句「可按编号取回」并保留 `fold_recall`。子代理里 `fold_pin` 照常可用——它只写进子会话自己的日志与账本，父代理看不到（父代理只接收最终回答），所以要交出去的结论必须写进最终回答。`fold_config` 在子代理里仍然只读；fork 子会话的账本汇总与关键词检索也只算本会话。
10. 「以后还要照着用」的内容靠 `fold_pin` 保住，不靠识别工具名或路径：用户明确提到记忆、备忘、技能、长期约定，或模型自己读到、写下以后还要照着用的内容时，读完就用 `fold_pin` 把接下来要用的那部分固化下来，允许逐字抄原文；临时看一眼、改一下就完的文件照常折叠。技能正文是要照着执行的步骤，加载后如果这一轮之后还要用，同样先固化再动手。插件不判断语义，也不按文件名自动保留——判断交给模型，代价是它可能忘记固化。

## 安装

profile 的 `package.json` 里加 link 依赖并把包名加进 `dsh.profile.bundles`：

```json
"dependencies": { "dsh-fold-context": "link:E:/dsh-fold-context" },
"dsh": { "profile": { "bundles": ["...", "dsh-fold-context"] } }
```

重启 DSH 生效。包内 `cordis.patch.yml` 负责把插件插进插件表。

## 配置

配置按「默认值 < profile 里的 `config` < `$DSH_HOME/fold-config.json`」合并，文件里的值最后生效。加载时越界值自动钳制、未知键忽略并写一条 warn，所以写错配置不会让插件起不来。

`fold-config.json` 是覆盖层而不是快照：单独 `set` 一个键时，只把这个键写进文件，profile 里的其它值不会被冻结（以后改 profile 仍然生效）。`reset` 会把**全部字段显式写成默认值**，所以它会盖过 profile；想回到 profile 的配置，删掉这个文件或把它改成 `{}` 再重启。升级默认值时，文件里没碰过的字段会跟着新默认值走。

文本型字段（`systemPromptText`、`recallReminderText`）还有一层：写盘时把「值恰好等于代码默认值」的键记进 `_fromCodeDefault` 清单，加载时这些键改取**当前**默认值。这样 `reset` 之后默认文案仍会随代码升级，不会把旧文案冻在文件里；自己写过的文案不等于默认值、不进清单，重启后保持原样。

`enabled` 是给对账用的总开关：关掉后插件对模型完全静默——不折叠、不注入折叠说明、也不注册 `fold_recall` / `fold_pin` / `fold_config` 三个工具，账单就等于「没装这个插件」。顶栏「折叠」页与插件设置页照旧工作（它们直接读载荷与配置文件），所以关掉之后还能从页面把开关打开；提示段与工具在下一轮重新挂上，不用重启。`foldSubagents` 在总开关打开后决定子代理会话是否也折：默认只在主会话折，子代理里留下 `fold_pin` 与（fork 的）`fold_recall`。

| 字段 | 默认 | 范围 | 作用 |
| --- | --- | --- | --- |
| `enabled` | `true` | 布尔 | 总开关。关掉后不折叠、不注入折叠说明、也不提供召回与固化工具；顶栏折叠页仍可用，用来核对未压缩的账单 |
| `foldSubagents` | `false` | 布尔 | 子代理会话（含 fork）是否也折叠。默认只在主会话折叠；子代理里不折、只注入一段短提示（pin 只对自己可见），但仍可用 `fold_pin` 记自己的备忘；fork 子会话保留 `fold_recall` 以读父会话的载荷 |
| `minFoldRatio` | `0.5` | 0.05~1 | 摘要 / 原文长度低于它才用摘要、给目录，否则保留原文；折叠检查点与目录整体按这个二选一；只决定折不折，不压缩摘要长度（检查点长度按精确值算） |
| `maxNoteTokens` | `300` | 20~1000 | 检查点里回复预览本身的 token 估算上限（元信息不占额度）；回复不超上限时原样保留，超过时 markdown 回复按实际标题摘要比较（长度按标题算出，不比原文短就保留原文），其它回复取开头+结尾 |
| `recallReminderAfter` | `1` | 1~50 | 同一段召回超过几次就提醒固化 |
| `recallReminderText` | 内置文案 | ≤2000 字 | 固化提醒，支持 `{count}` 与 `{tool}`；空串表示不提醒 |
| `recallIndexPreviewTokens` | `25` | 5~125 | 分段目录里每段预览的 token 估算上限；预览不比原文短时，这一行直接给原文 |
| `maxRecallTokens` | `1000` | 250~50000 | 单次召回返回的原文 token 估算上限（也用作分段目录与检索结果的额度） |
| `searchPreviewTokens` | `15` | 5~75 | 关键词检索结果里每段命中片段保留的 token 估算量 |
| `maxSearchFolds` | `8` | 1~50 | 关键词检索一次最多列几条折叠（更早的只给数量提示） |
| `maxPinTextTokens` | `0` | 0~50000 | 单条重要消息的正文 token 估算上限，`0` 表示不截断；设成正数只截断、不拒绝 |
| `maxPins` | `0` | 0~100000 | 重要消息条数的软上限，`0` 表示不限制；超了照常发布，只提示 |
| `pinBudgetTokens` | `0` | 0~2500000 | 全部重要消息的 token 估算软预算，`0` 表示不限制；超了照常发布，只提示 |
| `systemPromptText` | 内置文案 | ≤20000 字 | 系统提示段，支持 `{{recallTool}}`、`{{pinTool}}`、`{{configTool}}`、`{{minFoldRatio}}`；空串表示不注入 |
| `promptOrder` | `300` | -1000~10000 | 系统提示段的排序值，越小越靠前 |
| `foldToolOutputs` | `true` | 布尔 | `false` 时工具输出既不进摘要、也不进召回载荷，也不计入折叠判断的原文长度 |
| `maxFoldsPerTurn` | `8` | 1~32 | 一轮最多折成几段，超出的片段保留原文 |
| `maxStoreTokens` | `2000000` | 0~25000000 | 每个会话的 `fold-store` 载荷 token 估算上限，`0` 表示不限制；超了从最旧的折叠开始清理 |
| `cacheHitRate` | `1` | 0~1 | 前缀缓存的真实命中率（DeepSeek 实测约 97%）。只在没有 provider 回报时兜底；有回报时成本模型改用实测值 |
| `priceCacheHitInput` | `0.02` | 0~1000 | 缓存命中输入单价，元 / 百万 token（DeepSeek 谷时官方价） |
| `priceInput` | `1` | 0~1000 | 输入（未命中缓存）单价，元 / 百万 token（同上） |
| `priceOutput` | `4` | 0~1000 | 输出单价，元 / 百万 token（同上） |
| `peakPricing` | `true` | 布尔 | 按每条记录发生的时间分峰谷计价：峰时三档单价乘峰值倍率；关闭后全部按谷时价 |
| `peakMultiplier` | `2` | 1~10 | 峰时段的单价倍数，默认跟随计价服务；改离 `2` 时以设置为准，`1` 等于不区分峰谷 |

`recallReminderText` 的占位用单花括号，`systemPromptText` 的占位用双花括号，两者互不影响。

运行时用 `fold_config` 改配置：

- `fold_config({ action: "get" })`：返回当前生效配置、配置文件路径与每项取值范围。
- `fold_config({ action: "set", patch: { maxNoteTokens: 400 } })`：只接受上表白名单键，逐项校验；通过后写文件并立即生效。非法键或越界值整批拒绝，不会出现「改了一半」。
- `fold_config({ action: "reset" })`：把全部字段显式写成默认值并落盘，覆盖 profile 里的同名配置。

手工改 `fold-config.json` 也可以，但要重启 DSH 才生效；想让改动立刻起作用，用 `fold_config`。

## 数据落在哪

- 会话日志：检查点与重要消息都是普通 `user/message`，`source.kind` 分别是 `fold-checkpoint`、`fold-pin`。恢复/分叉照原样重放，不依赖插件在线。
- `$DSH_HOME/fold-store/<会话>.jsonl`：折叠原文、召回次数、重要消息快照、每轮实测用量（`usage` 记录）。实测与折叠无关：关掉总开关、或这一轮没折，provider 回报仍会落一条，账本才能拿它核对估算。召回靠折叠原文，删掉就只能看到检查点的摘要行。文件在首次访问时解析一次，之后走内存索引；超过 `maxStoreTokens` 时按会话从最旧的折叠开始清理，被清理的编号在召回时会明确说「已清理」，并保留一条 `prune` 记录。
- `$DSH_HOME/dsh-fold-context.log`：运行日志。

## 可视化调试

只有一处：顶栏「折叠」页。账本看 token 收支（下一节），模型视角看模型实际收到的历史——折叠检查点、被折叠的原文、召回与检索的痕迹、引用跳转，都能在那里点开对照。

早先那份单文件 HTML「逐轮报告」（`GET /fold-report`）与离线渲染脚本 `tools/render-report.mjs` 已经删掉：它是静态快照，而同样内容在模型视角里能点开、能互相跳转，还不会和账本口径分叉。

## 顶栏「折叠」页

插件自带客户端 bundle（`client/client.js`，手写 CJS，不需要构建），在会话顶栏注册一个「折叠」Tab（`conversation.view`，order 20）。页头（标题、两个子页标签、「更新于」）粘在视口上沿，翻明细表时不会滚丢；账本没有「刷新」按钮——每 5 秒自己拉，页头那行时间就是它的新鲜度。页面分两个子页：

- **账本**：每 5 秒拉一次同源 `GET /fold-stats?session=<会话 id>`，看 token 收支；另外每 20 秒拉一次 `GET /fold-composition?session=<会话 id>` 单独更新构成图，不跟整份模型视角一起重拉。
  - 顶部是「上下文构成」：折叠后与不折叠两条共用比例尺的堆叠条（以不折叠总量为满格，折叠后按比例缩短，不折叠条上有一道竖线标出保留位置）、九类占比表（系统提示 / 旧版系统提示 / 工具定义 / 用户原话 / 思考与回复 / 工具调用与结果 / 上下文注入 / 折叠摘要 / 重要消息），以及堆叠面积时间线（横轴每格是一轮或一次折叠/压缩事件；面积是当前视角，虚线是另一视角的总量，可切总量与每块增量）。时间线按会话事件重放，有压缩的会话会在压缩点看到掉下去的台阶；当前总量与 dsh-context 浏览器同口径（只算最后一条系统提示 + 工具定义 + 消息）。
  - 两张图左右并排（窄屏自动堆叠）：构成图回答「省掉的是哪一类」，趋势图回答「省下的量怎么累积」，并排放才方便对照，也不会被拉成一整条横线。
- **模型视角**：拉 `GET /fold-view?session=<会话 id>`，按轮展示 `session.deriveMessages()` 派生出的真实历史——也就是折叠后模型实际收到的样子；折叠检查点展开可对照被替换掉的原始内容。首包只带每轮的分组头与重要消息，展开某一轮时才用 `GET /fold-turn?session=<会话 id>&ordinal=<组号>` 取那一轮的条目：长会话整份历史有几十 MB，一次下发会让页面先卡在解析和内存上。
  - 重要消息不再单独汇总，而是按时间顺序贴在它出现的那一轮卡片之后，按级别分色常显（长期重要紫色、近期重要天蓝）、展开可读全文——汇总会丢掉「什么时候写下的」这条信息。
  - 召回留痕就地标出来：条目头逐次列出直接调用的 `fold_recall`（编号、段、筛选词），写在 `run_code` 脚本里的调用也认；检查点把折叠原文里的调用按次数汇总成「含召回 N 次」；轮卡片头显示这一轮的合计（召回 / 检索 / 被召回），页头再汇总整页——父级数字始终是子项之和。调用上的段不是照抄参数：有工具结果时以结果里实际返回的段为准，没有结果正文时才按 `parts` / `query` 解析；`parts: ["reply"]` 会写成「段 #128」，连续段压成「段 #195-#207」。三种方向的标签各一个颜色：召回黄、检索橘黄、被召回红——正文是灰的，靠色相才扫得出这段历史被谁取过。
  - 判断只认代码位置：`run_code` 的参数先按 JSON 解出 `code` 字段，再跳过字符串、模板与注释，只认 `tools.fold_recall({ ... })` 这种写法。文档、日志、回复里抄的示例不会点亮标记——宁可漏标，也不误标。
  - 「被召回」按折叠编号对召回流水，标在检查点上：取回的是原文，检查点本身没有被重发。分段召回再往下标一层：调用参数里的 `parts` / `query` 选中的第几段，就标在检查点原文列表的那一段上（目录行也带「召回×N」），展开前的标题给出「其中 N 段被召回 M 次」；轮卡片与页头的「段次」是这些段标记的和，父级仍然只做加法。
  - 召回返回的原文折起来看：模型视角里的 `fold_recall` 结果按工具自己写的段头切成一层层折叠条目（整段 / 分段 / 目录三种形态都认），标题写明取回几段、哪几段（`#195-#207`）、多少字、几段被截断；单次上限切在某段中间时，截断点单独标一行「原文 N 字 / 本次只返回前 M 字」，没取回的段也单列出来；取回的段多到一屏放不下时同样进限高滚动框。
  - 折叠原文面板里的分段目录默认收成一行（「分段目录 · 64 行 · 8.2k 字（≈2.0k token）」），点开才铺出那几十行；每段本身是独立折叠条目，标着段号、类型与被召回次数。目录是第一遍真正发给模型的东西，收起行就把目录自身的字数与 token 写出来——和标题行里原文合计是两个数，别混。段条目与目录行超过一屏时（20 段 / 40 行）装进限高滚动框：展开只多一屏，页面高度不随段数增长，切分点与「还有 N 段没取回」这类尾注留在框外。段里发起过的召回也标在段头：折叠原文里的调用以前只报到「含召回 N 次」，现在跟着段一起带出来，段条目的 chip 直接写「召回 f4 · 段 #128」。一条段被切成「思考 + 调用」两段时，标记只落在调用段上（按块归属 `recallCallBlocks`）——思考段不重复标，同一串 chip 出现两次是标错了位置，不是两条记录。
  - 召回调用与被召回的段可以互相跳：点调用上的 chip 打开面板，列出这次实际取回的段，点一条就展开那条折叠的检查点并滚到对应段；点段上的「被召回 N 次」反过来只列**这一段**的调用，点一条跳到那次调用所在的位置。落点精确到段：调用发生在折叠原文里时，服务端随调用下发它在原文里的段号（`partNo`），引用表记成 `{o, i, part}`，跳过去会依次展开检查点、折叠原文、那一段，而不是只停在检查点上。轮卡片上的「召回 N 次 / 被召回 N 次」也能点：那一轮的正文按需拉回来后再列成同一套可点条目。跳转只做定位——展开目标、滚动到看得见的地方、短暂描边，不复制原文。
  - 面板里的每条段落点都带那一段的正文开头（约 120 字，去掉段头 `[类型]` 前缀）；从段反查调用时，这一段自己的开头摆在面板顶部。预览按需取：面板打开时才读目标那一轮（按会话 + 轮次 + 数据版本缓存，同一轮只发一次请求），取不到时明写「没有取到这一段的正文」，不拿段号冒充内容。
  - 调用 chip 上的段以工具返回为准，不照抄参数：结果里只有 #195、#196，就标这两段（参数写 195-207 也一样）；整段召回写「整段 N 段」、只给分段目录写「目录 29/207 段」、失败写「未取回」并在悬停时给出原因（例如「没有匹配的段：reply」）。参数解析只在这条调用没有结果正文时兜底，老数据因此照旧显示。
  - 关键词检索的引用指向分段目录：只给 `query` 的调用没有单一折叠编号，它命中的是一条条折叠的目录。点它的 chip 打开的面板按折叠分组，每条先一行「f1a（第 1 轮）· 分段目录 · 命中 14/151 段」，再逐段列出命中的段号（各带那一段的正文开头）：点目录一行跳到那张目录，点段号跳到那一段。反方向也留痕——被检索过的目录收起行写「被检索 N 次」，目录行写「检索×N」，段头写「被检索 N 次」，检查点与轮卡片给出各自合计。「检索」不并进「被召回」的段次：检索没有返回原文，混在一起会让取回量虚高。命中的折叠不在这份历史里时只写清「另有 N 段命中但没列出来」，不推可点条目。

  - 「系统提示」只把最后一条非空 `system/message` 当当前版本；更早的版本留在 surface 里但不计入请求预测（dsh-context 浏览器与 provider 实际请求都按最后一条算），所以单列为「旧版系统提示（不计入）」，只作参考。
- 系统提示词按出现时间就地成块，不进轮次编号；第 1 版展示全文，第 2 版起默认只展示与上一版的差异（`+`/`-` 行、`@@` 段头），另给「查看这一版全文」。
  - 所有卡片默认收起，点开才取正文并挂进 DOM，一次展开大量原文也不会卡；召回结果同样按段收起，几万字的取回原文不会一次铺进页面。这是界面折叠，和插件的上下文折叠无关。
  - 总开关关掉时，页头显示一行说明：下方数字取自未压缩的会话，用来核对账单。同一页面仍可查看与改参数。

参数表单不在顶栏：它挂在原生「插件」页的 dsh-fold-context 组合包页面里（`plugins.bundle.config`，以组合包名为 key），和装了什么插件、开没开启放在一起。那里 `GET/POST /fold-config` 按同一张字段表渲染，保存即热生效，可一键恢复默认。顶栏只放当前会话的数据，改参数属于插件的一次性设置。

账本页显示（收益与成本都以 token 计，金额只作折算参考）：

- 四张卡：折叠收益（省下的 token）、召回成本（召回原文的输入开销；分段目录与关键词检索也花 token，同样计在这里）、重要消息成本（按模型此刻看得见的几条算，每次请求都要重发的部分）、净收益，单位都是 token。
- 每轮收支条形图：中间是零轴，右侧绿条是折叠省下的 token，左侧红条是这一轮召回与重要消息的开销。
- 折叠明细表：编号、轮次、原文字数、摘要字数、省下 token、被召回次数。召回次数偏高的段就该用 `fold_pin` 固化。
- 成本参考（按单价折算）：头部报折叠后累计 / 不折叠累计 / 净省的 token（按整段会话历史重放，含已被压缩卷走的轮次）；下面一行是计价口径——当前峰时还是谷时、峰时倍率、下次切换时间、总额里的峰时溢价；「按类别拆分（估算）」把三档 token 各自乘单价，给出折叠后、不折叠、净省的参考金额；「逐轮请求开销（估算）」把两种历史各重放一遍，给出每轮的净省 token 与实测输入；「实测账单」把 provider 回报的 `cacheRead` / `input + cacheWrite` / 输出三档照抄成金额，那是唯一贴近真实计费的一栏。
- 重要消息不在这页：它们的成本在这页的 KPI 里，正文按时间顺序列在「模型视角」页各轮之后。

估算口径与宿主 token-meter 一致：每 4 字符算 1 token，每个文本块再加 4 token；页脚写明该口径。旧记录缺轮次或大小字段时按字面量估算，并在界面上标记。

金额还要乘「之后还会重发多少次」：折叠省下的是每次请求都要重发的旧历史，所以省下的钱 = 体积差 × 重发步数 × 命中价。步数取自 fold 记录里的 provider 回报 `usage.steps`（同一轮折成多段时按轮去重）；没有回报的轮次按已知轮次的平均步数补，并在 `pricing.steps` 里标成 `estimated`。每一步的金额再按该条记录自己的时间戳取峰时或谷时单价。

### 三档单价与峰谷计价（不进收益口径）

折叠的收益一律用 token 报，不折算成人民币：真实请求还会被缓存命中率、请求期压缩器和工具定义改写，算出来的金额既无法验证、也不能跨会话比较。

金额只回答另一件事——「这些 token 按记录的时段与单价折算是多少」，出现在成本参考的表格与「实测账单」里，方便和 provider 的实际计费对账。

三个谷时单价都以「元 / 百万 token」为单位，在插件设置页（或 `fold_config` 的 `priceCacheHitInput` / `priceInput` / `priceOutput`）里改，默认取 DeepSeek 2026-11 的官方价目表（谷时）：命中 `0.02`、未命中 `1`、输出 `4`。峰时在谷时价上乘「峰值倍率」（`peakMultiplier`，默认 `2`；设成 `1` 等于不区分峰谷）。

- **峰谷按每条记录自己的时间戳判。** 折叠、召回、重要消息、实测用量记录各自带 `at`；成本按轮重放时用该轮 `turn/start` 的事件时间。历史记录因此按各自发生的那一刻还原，不会因为「现在是不是峰时」把整份账一刀切；跨午夜、跨切换点的记录各自落在自己的时段。
- **时段判定不写在本插件里。** 峰/谷、倍率与下次切换时间都问 fish-token 的 `fish.token` 服务（`getPricing(at)`）。倍率默认跟随服务报的 `multiplier`；本插件的 `peakMultiplier` 只在你把它改离默认 `2` 时覆盖（例如设成 `1` 让整份账不区分峰谷）。截至 2026-08-17，fish-token 的规则是北京时间周一至周五（不含法定节假日）09:00–12:00、14:00–18:00 为峰时；周末、法定节假日、午休与夜里都是谷时。窗口与节假日历都由服务维护，本插件不复制一份；面板会标出这次谷时的原因（周末、节假日、午休、夜间）与节假日历是否过期。服务不存在、查询抛错、或某条记录没有时间戳时，按峰值倍率保守估算（宁可把谷时记成峰时，也不要把峰时的账算少），面板把那一段标成「回退估算」并写清倍率；页头的「峰时溢价」就是这批 token 由峰值倍率多出来的钱。
- **溢价可拆。** 峰时溢价 = 峰时价 − 同一批 token 按谷时价，折叠后 / 不折叠 / 实测三个口径分开给。单价列在启用峰谷时标成「谷时单价」，峰时的行由服务端按倍率算好，页面不再拿一组均价乘总 token。
- 历史部分只算输入，而且要分档，不能用一个「命中率加权均价」：折叠省下的是之后每一次重发的旧历史，按缓存命中价（0.02）折；召回正文、检查点是**新内容**，第一次上行按未命中价（1）折一次，之后才按命中价。早先按 `0.02×0.97+1×0.03=0.0494` 的混合均价折，等于给方向相反的两件事同一个价：折叠收益高估 2.5 倍、召回低估 20 倍，净额的正负都可能算反。
- 输出部分两视角相同：同一句回复不管历史折叠与否都要生成一遍，所以输出金额出现在两份参考里、净省为 0。把它单列是为了让参考值与 provider 回报的口径对得上。
- 合计 = 三档金额相加；金额按未取整的逐条金额累加后再统一取整，不逐行取整后相加，避免分位误差。召回按返回正文的 token 折一次未命中；重要消息先按未命中折一次，之后每一步请求按命中价常驻。

### 成本估算的口径

折叠省的是「每轮都要把历史重发一遍」的成本，所以不能只看上下文末态大小。估算按轮重放：

- 一轮有 `k` 步，前缀被重发 `k` 次；轮内新增内容按平均半步处在上下文中。
- 峰谷按记录的时间戳：折叠、召回、pin、usage 各用记录里的 `at`，全量历史重放用 `turn/start` 的事件时间。没有时间戳的轮次按峰时保守估算，数量记在 `cost.peak.turns.unknown`，页面会写明。服务拿不到时整份账按峰值倍率回退，`cost.peak.fallback` 为 `true`。
- 前缀缓存只认上一次请求里出现过的内容。折叠在轮末改写了历史，所以上一轮的检查点到本轮首请求是**未命中**，不能算进命中前缀。
- 单轮重放量 = `k × 前缀 + 新增 × (k−1)/2`，其中前缀按 `hitRate` 拆成命中与未命中两档；新增内容与上一轮检查点各按未命中价折一次，检查点在本轮其余步里按命中价重发。收益本身只看 token，金额见上一节。
- 未命中不随体积放大：真正没命中的是「上一次请求之后才写进历史的内容」——每步的思考/回复/工具结果，两种视角都要付一次。折叠视角还额外付四样新内容：检查点摘要、固化消息、召回返回的正文、分段目录与关键词检索（`cost.pluginOverhead` 按这四样分档，本会话约 1.5 万 token）。分段目录也是 `fold_recall` 的工具结果，同样按未命中计一次——它不带原文，但确实是一段新写进上下文的正文。所以不折叠视角的未命中 = 折叠视角扣掉这三样，只会更小；体积差全部落在命中的前缀里（本会话命中 64M vs 327M）。早先的版本对两种视角都套「未命中率 × 重发量」，等于假定未命中与体积成正比，把 6 倍体积算成 6 倍未命中（4000 万 token，比折叠视角的 680 万凭空多出三千多万）。
- 拿到过 provider 回报时，成本模型用实测总量反推两个校准系数：`promptScale` 把重放量缩放到真实请求量（请求期压缩器还会收缩上下文），`outputScale` 缩放输出。实测来自每轮结束时单独落下的 `usage` 记录，不依附折叠：关掉总开关、或这一轮没折，账本仍然拿得到账单；升级前跑过的轮次可以用 `node tools/usage-backfill.mjs <会话 id>` 从会话日志补。命中率分两个数：`hitRate` 是 provider 原样回报的 `cacheRead / (cacheRead + input)`，用于展示；`resendHitRate` 从分母里扣掉每步新增内容，才是真正用于拆档的那个——新增内容按定义必定未命中，留在分母里会把纯重发的命中率系统性压低。系数是算出来的、不是手调的，只由有回报的轮次决定，再套回全部轮次。
- 同一套式子套在「不折叠」的历史上得到对照值，两者相减是净节省。没被折叠的短回合整段仍算新内容，不会虚增节省。
- 重放的底稿是**整段会话历史**，不是模型此刻看得见的那一截：官方压缩（`compact-checkpoint`）会把旧轮从 surface 里整段换掉，只看派生消息的话，被换掉那几轮的账会跟着消失，净省当场归零。所以成本从会话事件重放（`lib/history.js`）：每一轮记下它**开始时**的上下文体积（折叠后 / 不折叠各一份），压缩之后基准跟着变小（趋势图上就是那个台阶），但之前各轮已按当时的基准结算过，不再重算。事件日志读不到（老宿主、没有日志）时才退回派生消息。
- 两侧都跟着压缩台阶下降：压缩在「不折叠」的世界里同样会发生，所以不折叠基准也按当时还活着的原文算，不会把已经被卷走的原文永远算在头上。
- 旧折叠记录可能没写 `unfoldedChars`（插件早期版本）。这时反事实会拿折叠后的体积当下界，并把这类轮计进 `totals.unfoldedEstimatedTurns`——早先直接留 0，累计体积不增长，净节省会算出荒谬值。

这是估算，不是账单：它量的是会话历史，而真实请求还可能被请求期压缩器（如 billion-context）改写。所以账本把 provider 回报的「实际请求」并排显示，并在 `cost.drift` 里把差额拆成三段：`governedTokens`（归折叠管的部分——插件生效后的历史加当前系统提示，这一份才和实测并排比）、`legacyTokens`（插件生效前那一轮，没人折得动，实测里早被请求期压缩器改写了）、`externalTokens`（实测里剩下的历史外开销：工具定义、请求期摘要）。差得太多就说明上游还有一层在压缩。同一轮被轮内发言切成多组、或折成 f2a / f2b 多段时，成本按轮合并成一行，不重复计费。`fold_recall` 与 `fold_pin` 的开销按召回/发布时的字符数单算，不进这套重放。


「模型视角」页顶部的合计与账本用同一套公式，但只给折叠产物（检查点、重要消息、被折叠的原文）计价，不含系统提示词与工具定义，所以会比侧栏「上下文」页的当前占用小一截；后者的总量含这两项。侧栏「上下文」页（dsh-context）还把工具调用的名字与参数各算一块，本插件同样这么算，因此同一批消息的估算值可以互相对照。

`/fold-stats` 只读 `fold-store` 的记录，不需要会话活着；`/fold-view`、`/fold-turn` 与 `/fold-composition` 都要读 `session.deriveMessages()`，会话不在进程里就返回 404。会话 id 可以带 `session-` 前缀，也可以只传纯 uuid（服务端会自己补前缀，命中哪个形状就用哪个）。这五个路由里除 `/fold-config` 都用 `session` 参数定位会话，缺了返回 400（`/fold-turn` 还要 `ordinal`，缺了同样 400）；找不到会话返回 404——`/fold-stats` 在「既没有账本、也解析不到会话」时同样返回 404，不再回 200 空账本；`/fold-config` 另接受 `POST`（`{patch}` 或 `{reset:true}`），其余路由只接受 `GET`/`HEAD`。所有 `/fold-*` 只接受本机同源请求：`Host` 必须是回环地址（防 DNS rebinding），`Origin` 存在时必须与 `Host` 一致（防跨站读取历史），`POST` 必须是 `application/json`（跨站简单请求带不了这个类型，从而挡掉 CSRF）。不满足返回 403。宿主没有 `webServer` 时这个 Tab 不会出现，折叠不受影响；宿主没有插件页（缺 `ui-plugin-manager`）时参数表单也无处渲染，`fold_config` 工具照旧可用。

## 和 billion-context 共用

billion-context（本地代理式压缩）与本插件在不同层工作：前者在请求发往模型之前重写历史，不写 DSH 会话日志；后者用 surface 替换把折叠结果落进日志。两者能同时跑，没有谁会把谁弄坏，但要知道这四件事：

1. **「永不折叠」只在本插件这一层成立。** billion-context 会把它的压缩块范围内的所有消息再摘要一遍，包括我们的检查点与 `fold_pin` 重要消息。模型可能看不到某条重要消息的原文，也看不到某轮的折叠编号；`fold_recall("f7")` 仍能凭本地 `fold-store` 按编号取回原文，所以编号别丢（它在检查点正文里）。
2. **每次折叠都改变请求前缀。** billion-context 下一请求会按 resync 全量重发，这是它的账单成本；折叠本身不另外收费。
3. **两边都在缩减历史，收益会重叠。** 账本上的「省下」是本插件这一层的；代理层再省多少，要看 billion-context 自己的统计。
4. **官方压缩（`compaction-basic`）会把重要消息一起卷进摘要，插件不补发。** 它把旧历史换成一条 `compact-checkpoint` 摘要，插件把这个检查点当 keeper（下一轮不再折它），但不把被卷走的 `fold_pin` 重新 append 回末尾：pin 是「这一轮觉得值得常驻」的判断，不是永久存储，长会话里重要性会随时间淡化，淡化交给压缩层。被卷走的 pin 不再回到上下文，也不会进 `fold_recall`（它只召回折叠原文）。

如果确实需要某些结论在代理层之上也常驻，可以把 `fold_pin` 的内容注入系统提示词（`PromptSection.text` 支持函数形态），代价是每次 pin 变化都会让前缀缓存失效一次；v1 没做。

## 已知限制

- 召回文本按会话存在 `$DSH_HOME/fold-store/`：分叉出来的新会话按编号召回时会只读回退到父会话的载荷，前提是父会话仍在当前进程里；父会话已关闭或查不到时返回「暂时读不到」。账本汇总与关键词检索不跨父，避免把父会话的折叠重复计价。
- 每次替换都会让请求前缀变化，接在后面的压缩代理（如 billion-context）下一次请求会全量重发一次；这是折叠的固有成本。
- 只折叠插件在线期间观察到的轮次：插件装上之前的历史保持原样。
- 关键词检索只搜本会话 `fold-store` 里的折叠原文：重要消息与用户原话本来就在上下文里，不参与检索；分叉会话搜不到父会话的载荷（按编号单读可以）。检索只定位，不判断内容是否已过时——文件改过没有，看摘要里的「· 文件：改过 …」。
- 官方压缩把 `fold_pin` 卷进摘要后，插件不补发、模型也取不回那条 pin；账本只能把还活着的会话里「已经看不见的 pin」标成「已压缩」并只报体积（`pinLostTokens`）、不再进成本；会话不在进程里时仍按旧口径估算。没装请求期代理又开回了默认压缩时，这个偏差才会出现。

## 评测

完整方法见 [docs/evaluation.md](docs/evaluation.md)。一句话：**经济性可以对账，质量只能同任务开关对照。**

离线评测器只读会话日志里 provider 回报的用量与 `fold-store` 的记录，不读账本的反事实估算，所以算出来的金额能直接和账单比：

```
node tools/eval.mjs --list
node tools/eval.mjs <会话 id> [--home <DSH_HOME>] [--json]
node tools/eval.mjs --ab <开了折叠的会话> <对照会话>
```

输出每轮的实测 prompt / 未命中 / 输出 / 金额，以及折叠段数、召回次数与模式、重复召回、跨轮重复调用这些质量线索。
